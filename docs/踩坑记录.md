## Bug 1：Jackson 命名坑（踩了两次）

### 现象

前端页面显示 `(, )` / 空白，坐标值取不到。

### 排查过程

```bash
# 查接口实际返回
curl -s "http://localhost:8080/api/locations?pageSize=1"
```

返回：
```json
{"xcoord": 86, "ycoord": 0, "zcoord": 2}
```

**返回的是全小写 `xcoord`，但前端代码取的是 `xCoord`。**

### 根因

Java 字段命名 `xCoord` 时，Lombok 生成 `getXCoord()`。
Jackson 在解析属性名时，对「**单字母前缀 + 大写字母**」这种命名有异常行为，会解析成**全小写**。

```
Java 字段:   private Integer xCoord;
Lombok 生成: public Integer getXCoord()
Jackson 解析: xcoord          ← 错了！
期望:        xCoord
```

### 解决方案

```java
@JsonProperty("xCoord")     // 显式指定 JSON 字段名
private Integer xCoord;
```

### 影响范围

**踩了两次**：
1. `LocationVO`（库位列表页坐标为空）
2. `PickingTaskVO`（波次详情页坐标为空）

第二次之后做了全量扫描，确认只有这两个 DTO 受影响。

### 教训

> **Java 里不要用「单字母 + 大写字母开头」的字段名**（如 `xCoord`、`aValue`），
> 容易在序列化时踩坑。如果一定要用，**必须加 `@JsonProperty`**。

**面试可以这样讲**：
> "我遇到过 Jackson 序列化的命名问题——Java 字段叫 `xCoord`，Jackson 解析出来变成 `xcoord`，
> 导致前端取不到值。原因是 Jackson 对单字母前缀的命名处理有特殊规则。
> 解决是显式加 `@JsonProperty`。这个坑我踩了两次，第二次之后做了全量扫描确认影响范围。"

## Bug 2：测试写死 ID 导致误判

### 现象

调用拣货接口报错：
```
拣货失败：库位 988 的已分配量不足（可能已被释放）
```

### 排查过程

1. 查库位 988 的库存 → 该库位没有任务说的那个 SKU
2. 查分配明细 → **查不到该波次的任何分配明细**
3. 查波次表 → **发现表里已有 9,707 条波次数据！**

**真相**：`picking_wave` 表里已经有导入的 9,707 条**真实历史波次**，
所以新生成的波次 ID 是 **9708**，不是 1。

而我的测试脚本写死了 `POST /waves/1/pick` —— **拣的是导入的历史波次**（它没有分配明细）。

### 解决方案

测试脚本改用**接口返回的动态 ID**，不硬编码。

### 教训

> **测试时不要硬编码 ID**，尤其是当表里已有数据的时候。
> 应该用接口返回的 ID，或先查一遍。

**面试可以这样讲**：
> "我遇到过一个'假 Bug'——接口报库存不足，排查半天发现是我测试脚本写死了波次 ID。
> 因为表里已经有导入的 9,707 条历史数据，新建的波次 ID 是 9708 而不是 1。
> **代码没问题，是测试方式错了。**"

## Bug 3：期初流水生成时机导致对账不一致

### 现象

库存对账功能报出 **8 条不一致**：
```
56TC1Z-11 @ L-04-23: 库存表=49  流水累计=48  差异=1
```

### 排查过程

1. 对账逻辑：`inventory.qty` 应该等于该 (SKU,库位) 所有流水的 `qty_delta` 之和
2. 差异 = 1，说明库存表比流水多 1
3. 回溯操作顺序发现：
   - 先做了**发货测试**（库存 50 → 49）
   - **之后**才生成期初流水
   - 所以期初流水记的是 **49**，而不是 50
   - 加上发货的 -1 → 累计 48，而库存表是 49

### 解决方案

重新初始化：清空 → 生成库存 → **立即生成期初流水**（此时库存是干净的初始值）→ 对账通过。

### 价值

**这恰好证明了对账功能有用**——它真的查出了数据不一致。

**面试可以这样讲**：
> "我做了个库存对账功能，用流水累加重算库存再与库存表比对。
> 结果真的查出 8 条不一致——排查发现是期初流水生成时机的问题。
> **如果哪天有人直接改数据库没记流水，这个功能立刻能发现。**"

## Bug 4：curl 传中文参数编码错误

### 现象

调创建接口报 500：
```
Invalid UTF-8 start byte 0xb2
```

### 根因

Windows 终端默认用 **GBK 编码**，curl 命令行里的中文被编码成 GBK 字节流，
而后端按 UTF-8 解析，就报错了。

### 解决方案

**两步走**：
1. 用 Python 把 JSON 写成 **UTF-8 文件**
2. curl 用 `--data-binary @文件` 传

```bash
python -c "import json; open('req.json','w',encoding='utf-8').write(json.dumps(body, ensure_ascii=False))"
curl -X POST ... -H "Content-Type: application/json" --data-binary @req.json
```

### 教训

> Windows 开发时，**命令行传中文要注意编码**。用文件传是最稳的方式。

## Bug 5：端口被占用导致启动失败

### 现象

```
Web server failed to start. Port 8080 was already in use.
```

### 排查与解决

```bash
# 找到占用端口的进程
netstat -ano | grep ":8080.*LISTENING"

# 结束进程
taskkill //F //PID <PID>
```

### 教训

> 重启服务前先确认旧进程是否已停止。
> 可以写个脚本：**先杀端口 → 再启动**。

## Bug 6：vite 代理前缀与前端路由撞车

### 现象

访问 `http://localhost:5173/agent` 页面，浏览器显示：

```json
{"detail":"Not Found"}
```

（这是 FastAPI 的 404 响应，不是 Vue 页面）

### 排查过程

1. 页面返回的是 JSON 而不是 HTML → 说明请求**没到前端**，被代理转走了
2. 检查 vite 代理配置发现：
   ```js
   proxy: {
     '/api':   { target: 'http://localhost:8080' },
     '/agent': { target: 'http://localhost:8000' }   // ← 问题在这
   }
   ```
3. 而前端路由里也有 `/agent`：
   ```js
   { path: 'agent', component: AgentView }   // ← 撞车了
   ```

**根因**：vite 的代理匹配优先级高于前端路由。
访问 `/agent` 时，代理规则先命中，请求被转发到 Python 服务（8000），
而 Python 服务没有 `/agent` 这个路径 → 返回 404。

### 解决方案

把代理前缀改成**不会和路由撞车**的名字：

```js
proxy: {
  '/api':       { target: 'http://localhost:8080' },
  '/agent-api': { target: 'http://localhost:8000',
                  rewrite: (path) => path.replace(/^\/agent-api/, '') }
}
```

同时前端请求的 baseURL 也从 `/agent` 改为 `/agent-api`。

### 教训

> **代理前缀不要和前端路由重名。**
> 常见做法是给接口统一加后缀，如 `/api`、`/agent-api`、`/py-api`，
> 而前端路由用业务名，如 `/agent`、`/routing`。

**面试可以这样讲**：
> "我遇到过一个前后端路由撞车的问题——vite 的代理前缀 `/agent`
> 和前端页面路由 `/agent` 重名，导致访问页面时请求被代理转发走，返回 404。
> 排查方法是看返回的是 HTML 还是 JSON——返回 JSON 说明请求没到前端。
> 解决是给代理前缀加个后缀，和路由名区分开。"
