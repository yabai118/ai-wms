## 一、项目概述

### 1.1 一句话介绍

**一个"Java 业务底座 + Python 智能 Agent"的融合型仓储管理系统，
基于真实企业数据，用算法优化仓库作业效率。**

用一句更好懂的话说：
> **传统仓储系统只负责"把库存记准"；这个项目在此之上，还让系统"自己算"——
> 商品该放哪个位置、拣货员该按什么顺序走，都由算法给出建议。**

### 1.2 项目要解决的问题

一个仓库每天面临的核心问题是：

| 问题 | 后果 |
|---|---|
| 库存记不准、超卖 | 客户下单了却发不出货 |
| 商品随便放 | 高频商品放在仓库深处，拣货员每天多走很多路 |
| 拣货顺序随意 | 一个订单在仓库里来回跑，效率低 |
| 算法/服务出故障 | 业务停摆 |

本项目针对这四类问题分别给出技术方案（详见[第四章](#四关键技术实现)）。

### 1.3 数据来源 ★

**这是本项目区别于一般"学生练习项目"的关键。**

数据来自：**巴西某鞋类制造企业真实 WMS（仓储管理系统）用 SQL 导出的生产数据**，
相关论文发表于学术期刊 *Data in Brief*（2025），采用 CC BY 4.0 开源许可。

| 数据项 | 规模 |
|---|---|
| 商品 | 208 个鞋款（A 类 44 / B 类 70 / C 类 94） |
| SKU（商品款 × 尺码） | **2,515 个** |
| 库位 | **2,292 个**（含三维坐标） |
| 客户订单 | **32,634 个**（共 122,370 行明细） |
| 拣货波次 | **9,707 个** |
| 时间跨度 | **286 天**（2023 年 1 月 – 10 月） |

**这些数字是真实的，不是我构造的。**

## 二、系统架构

### 2.1 整体架构

系统由**三个服务**组成：

```
┌─────────────────────────────────────────────────────┐
│              Vue3 管理后台（11 个页面）               │
└──────────────┬──────────────────┬───────────────────┘
               │ /api             │ /agent-api
┌──────────────▼──────────┐  ┌────▼──────────────────┐
│  Java 业务底座           │  │  Python Agent 层       │
│  Spring Boot 3 + MyBatis│  │  FastAPI               │
│  ├ 商品 / 库位 / 库区    │  │  ├ 编排器（路由/校验/降级）│
│  ├ 入库（收货/上架）     │  │  ├ 路径优化（3 种策略）  │
│  ├ 出库（分配/波次/拣货）│  │  └ LLM Agent（查询/解释）│
│  └ 库存（五字段模型）    │  │                        │
└──────────────┬──────────┘  └────┬──────────────────┘
               │                  │
        ┌──────▼──────────────────▼──────┐
        │   MySQL 9（19 张表）+ Redis      │
        └────────────────────────────────┘
```

**为什么分成两个后端服务？**

Java 负责"**业务**"（事务、权限、数据一致性），Python 负责"**算法**"（路径优化、智能决策）。
这样设计的好处：
- 业务迭代不影响算法，算法调整不动核心交易链路
- 各自用最擅长的技术栈（Java 做企业级业务、Python 做数据处理与算法）

### 2.2 技术栈

| 层 | 技术 | 用在哪 |
|---|---|---|
| **Java 后端** | Spring Boot 3.2 + MyBatis-Plus | 业务逻辑、数据持久化 |
| | MySQL 9 | 19 张表 |
| | **Redis** | **库存缓存**（Cache-Aside 模式） |
| | EasyExcel | 数据导入 / 导出 |
| **Python Agent** | FastAPI + Pydantic | 算法服务 |
| | PyMySQL + pandas | 数据处理 |
| | **OpenAI SDK** | 调用大模型（通义千问），实现自然语言查询 |
| **前端** | Vue3 + Vite + Element Plus | 11 个管理页面 |
| | ECharts | 数据看板、库存地图、路径可视化 |

> **完整技术栈说明见 [README](../README.md)。**

### 2.3 关键架构决策

**① 为什么用"模块化单体"而不是微服务？**

行业实践表明：**微服务适用于团队规模 > 30 人**的场景。
本项目是单人开发，采用**模块化单体**——按业务域划分模块
（`wms-inbound` / `wms-outbound` / `wms-inventory` 等），
既保持了开发效率与数据强一致性，又为未来拆分预留了边界。

> **这一点在面试中是加分项**：说明我理解"技术选型要匹配规模"，
> 而不是盲目堆砌微服务全家桶。

**② 为什么不用消息队列（MQ）？**

本系统的服务间调用是**同步的**（Java 请求 Python 算路径，需要立刻拿到结果），
不需要异步削峰或解耦。引入 MQ 只会增加复杂度。**这是有意识的取舍。**

**③ Redis 的定位：只做缓存，不做分布式锁**

低并发场景下，数据库的"条件更新"已足够保证库存不超卖（见 [4.2](#42-并发扣减防超卖)），
分布式锁是**秒杀场景**的方案，用在这里是过度设计。

## 四、关键技术实现

> 本章是全文档的技术核心，也是简历里最值得写的部分。

### 4.1 库存五字段模型

**问题**：库存用"一个数字"表示够不够？

**不够。** 因为库存处在不同的状态中：有的被订单占住了、有的正在被拣货员取走、
有的因为质检不合格被冻住了……用一个数字无法表达。

**本项目的设计**：库存表用**五个数量字段**分别记录不同状态。

| 字段 | 含义 | 生活类比 |
|---|---|---|
| `qty` | 现有总量 | 冰箱里一共有 10 瓶牛奶 |
| `qty_allocated` | 已分配给订单 | 其中 3 瓶已被订单预定，别人不能拿 |
| `qty_picked` | 已拣出未发货 | 2 瓶已拿在手上，还没出库 |
| `qty_onhold` | 冻结 | 1 瓶发现过期，锁住不能动 |
| `qty_available` | **可用量** = 总量 − 已分配 − 冻结 | **实际还能卖的 = 4 瓶** |

**为什么必须这么设计**：

1. **防超卖**：订单必须先"占住"库存（`allocated`），别人就不能再卖
2. **符合真实作业**：拣货员取走货但还没发货时，库存"总数"不应减少（货还在仓库）
3. **异常可表达**：质检不合格的货要"冻住"，与正常占用区分开

**实测效果**（一次分配操作前后）：

| | 现有总量 | 已分配 | 可用量 |
|---|---|---|---|
| 分配前 | 25 | 0 | 25 |
| **分配后** | **25（不变）** | **1** | **24** |
| 拣货后 | 25（不变） | 0 | 24（已拣出 1） |
| 发货后 | **24（这时才减）** | 0 | 24 |

### 4.2 并发扣减防超卖

**问题**：多个订单同时抢同一批库存，如何保证不超卖？

**超卖举例**：库存只剩 1 件，两个订单同时下单，两个都读到"有 1 件"，
各自确认成功，最终卖了 2 件，库存变成 −1。

**本项目的解法：条件更新**

```sql
UPDATE inventory
SET qty_allocated = qty_allocated + 1,
    qty_available = qty_available - 1
WHERE sku_id = 100
  AND location_id = 5
  AND qty_available >= 1      -- ★ 把"够不够"写进 WHERE 条件
```

**为什么这样就安全**：数据库在执行这条语句时会**加行锁**，
"判断库存够不够"和"扣减库存"变成了**一个不可分割的操作**。
两个并发请求会排队执行——第一个扣完，第二个再判断时发现不够，直接失败。

**实测（并发压测）**：

| 场景 | 库存 | 并发订单 | 成功 | 失败 | 结果 |
|---|---|---|---|---|---|
| 1 | 100 | 225 | **100** | 125 | ✅ 无超卖 |
| 2 | 50 | 204 | **50** | 154 | ✅ 无超卖 |
| 3 | 20 | 185 | **20** | 165 | ✅ 无超卖 |
| 4 | 10 | 156 | **10** | 146 | ✅ 无超卖 |

**每个场景都是"成功数恰好等于库存数"**，说明零超卖。
性能：QPS 最高 908，P99 延迟 < 380ms。

### 4.3 Redis 缓存

**问题**：出库前每次都要查"这个商品还有多少可用库存"，
高频查询会给数据库造成压力。

**本项目的解法：Cache-Aside（旁路缓存）模式**

```
读：先查缓存 → 命中直接返回
             → 未命中 → 查数据库 → 把结果写回缓存

写：更新数据库 → **删除缓存**（而不是更新缓存）
```

**为什么"写的时候删缓存"而不是"更新缓存"**：
更新缓存有并发顺序问题——两个请求先后更新数据库和缓存，
如果顺序错乱，缓存里会留下旧值。删除缓存则让下次读自然回源，更简单也更可靠。

**三个防护措施**：

| 问题 | 现象 | 做法 |
|---|---|---|
| 缓存穿透 | 查询不存在的数据，每次都打数据库 | 空结果也缓存（但过期时间短） |
| 缓存雪崩 | 大量缓存同时过期，数据库被瞬时打垮 | 过期时间加**随机偏移** |
| 缓存击穿 | 热点数据过期的瞬间，大量请求同时回源 | 本场景数据量小、回源快，不处理 |

**★ 一个容易被忽略的细节：事务提交后才删缓存**

如果直接在事务里删缓存，会有这样的问题：
```
时间线：
T1: 更新数据库（还没提交）→ 删除缓存
T2: 读缓存发现没有 → 读数据库（此时看到的是旧值）→ 把旧值写回缓存
T1: 事务提交（数据库已是新值）
结果：缓存里是旧值，与数据库不一致 ❌
```
所以本项目用 Spring 的 `TransactionSynchronization`，
**在事务提交之后**再删缓存，上述窗口就不存在了。

**实测**：首次查询 592ms（回源）→ 再次查询 **0ms**（命中缓存）；
库存变动后缓存自动清除，再查拿到新值。

### 4.4 拣货路径优化

**问题**：一个拣货波次包含多个货位，拣货员按什么顺序走最省力？

**仓库布局**（从真实导航点数据推断）：

```
x=66   LC 通道（左侧）┐
                       ├─ Block1（货架区1）
x=403  CC 通道（中央）┤
                       ├─ Block2（货架区2）
x=686  RC 通道（右侧）┘
```
即 **3 条纵向通道 + 2 个货架区块**，是仓储运筹学中典型的「双区块布局」。

**实现的三种行业标准策略**：

| 策略 | 核心思想 |
|---|---|
| **返回式（Return）** | 每条通道从入口进、取完原路返回 |
| **S形（S-shape）** | 蛇形穿越：通道 1 从下往上，通道 2 从上往下，循环 |
| **最大间隙（Largest Gap）** | 找出通道内最大空隙，只走到空隙处折返，不白跑 |

**实测结果（单波次示例）**：

| 策略 | 总距离 | 相比基线 |
|---|---|---|
| 顺序拣货（基线） | 12,127 米 | — |
| 返回式 | 11,586 米 | −4.5% |
| **S形** | **9,554 米** | **−21.2%** |
| 最大间隙 | 11,586 米 | −4.5% |

**批量实验（100 个真实波次）**——单波次可能恰好合理，统计才有说服力：

| 指标 | 值 |
|---|---|
| **平均节省** | **12.4%** |
| 中位数节省 | 10.5% |
| 最大 / 最小 | 47.2% / 0.0% |
| S形胜出次数 | 66 / 100 |

**一个有意思的发现**：学术界结论是"最大间隙策略在小订单量下最优"，
但在本仓库布局下 **S形更优**——因为本仓库只有 3 条通道，
通道间切换成本高，而最大间隙需要从两端分别进入通道，
额外的纵向移动抵消了它的优势。

> **这说明算法效果依赖具体布局，不能照搬文献结论。**
> 我做了对比实验才发现这一点，而不是直接套用教科书答案。

### 4.5 Agent 编排与三级降级

**问题**：算法服务可能因各种原因不可用（超时、异常、结果不合法），
不能因为算法挂了就让业务停摆。

**本项目的解法：编排器 + 三级降级**

编排器负责四件事：
1. **任务路由**：按任务类型分发给对应模块（确定性逻辑，不是让 AI 自由决定）
2. **上下文管理**：统一组装各模块需要的输入，避免重复查数据库
3. **结果校验**：算法输出必须检查合法性，**不能盲信**
4. **降级决策**：失败时切换到备用方案

**三级降级管线**：

```
① 算法正常        → 成功（最优结果）
② 规则桩兜底      → 降级（结果质量下降，但业务可用）
③ 都失败          → 失败（生成人工工单）
```

**规则桩是什么**：每个决策模块都有一个"最简单的备用规则"，保证一定算得出来：

| 模块 | 规则桩 |
|---|---|
| 路径优化 | 按库位编码顺序拣货 |
| 需求预测 | 最近 7 天移动平均 |
| 货位分配 | ABC 分类就近 |
| 异常诊断 | 按类型返回预置文案 |

**实测**：主动注入故障验证降级是否生效——

| 注入的故障 | 结果 |
|---|---|
| 算法异常（不存在的波次） | **降级**，规则桩接管，业务不中断 |
| 参数非法（错误的策略名） | **降级** |
| 未知任务类型 | 失败（需人工处理） |
| 正常任务（对照组） | 成功（28ms） |

**并且做了监控面板**，可以实时看到**降级率**——这证明降级设计是
"真在运行、可观测"的，而不是只写在文档里。

**LLM 用在哪、不用在哪**（同样是有意识的取舍）：

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 预测 / 货位 / 路径 | ❌ 不用 LLM | 要可解释、可复现、可验证，LLM 做不到 |
| 异常**检测** | ❌ 用统计规则 | 3σ 等统计方法确定性强 |
| 异常**解释** | ✅ 用 LLM | 把异常数据翻译成人话，是 LLM 的强项 |
| **自然语言查询** | ✅ 用 LLM | 理解中文提问 → 调用工具查数据 → 组织回答 |

**自然语言查询的实际效果**（用中文直接问系统）：

```
问：仓库现在有多少库存？
答：当前仓库总库存为 125,976 件。

问：8N10W9-11 这个 SKU 分布在哪些库位？
答：分布在 Q-13-13（34件）/ M-01-30（32件）/ P-06-12（32件）

问：哪些拣货员作业量最少？
答：作业量最少的拣货员是 Operator_21，仅完成 2 波次作业。
```

**技术原理**：LLM **不直接算数**——它只负责"理解意图，决定调用哪个工具"，
数据由系统查数据库获得，最后 LLM 把结构化数据组织成人话。

**性能**：QPS 436 ~ 908 ｜ P50 43 ~ 186ms ｜ P99 80 ~ 374ms

### 5.2 拣货路径优化（100 个真实波次）

**平均节省 12.4% 行走距离**，S形策略在 66% 的波次中胜出。

### 5.3 Redis 缓存

首次查询 592ms → 命中缓存 **0ms**；库存变动后缓存自动失效。

### 5.4 数据导入导出

- **导入**：Excel 批量导入商品/库位/期初库存，含逐行校验与错误明细
- **导出**：分批查询 + 流式写入，**内存占用恒定**，不随导出行数增长

## 七、诚实说明

> **这一节很重要**：面试中如实说明项目的边界，比夸大更可信。

### 7.1 数据真实性

| 数据 | 性质 |
|---|---|
| 商品、库位、订单、拣货波次 | ✅ **真实**（企业 WMS 导出） |
| 库位坐标（22 个补充库位） | ⚠️ **推断**（原始数据缺失，按编码规律推算） |
| 库位类型（存储区/拣货区） | ⚠️ **推断**（根据"是否被拣货使用过"判定） |
| 期初库存 | 🔧 **构造**（用真实订单出货量反推） |
| 入库数据 | 🔧 **构造**（公开数据集只有出库侧数据） |

### 7.2 未实现的功能及原因

| 未实现 | 原因 |
|---|---|
| **货位分配优化** | 数据集自带的 `Class_Based_Storage` 就是"按 ABC 摆放"的方案。如果我只做"按 ABC 摆"，只是**复现基准，没有增量**。要做出价值必须超过 ABC（如加入商品关联度、容量约束优化），时间有限的情况下，优先做了 JD 明确要求的"调度编排 + LLM Agent" |
| **需求预测** | 已预留接口 + 规则桩，未实现完整算法 |
| **库存盘点** | 时间不足，砍掉 |

### 7.3 一个真实的排查案例（体现工程能力）

开发导出功能时，导出 3.2 万条订单**却只有 500 行**。
排查发现项目里有两层分页上限把导出也卡住了。

**但我没有简单地把上限调大**——因为一次性把 3 万条查进内存本身就是错的，
数据量再大就会内存溢出。

**改为「分批查询 + 流式写入」**：每批查 500 条、立即写入 Excel、再查下一批，
内存占用恒定，数据量再大也不会出问题。

> 这类"发现问题 → 分析根因 → 选择正确方案"的过程，
