## 一、项目概述

### 1.1 一句话介绍

**一个「Java 业务底座 + Python 智能 Agent」的融合型仓储管理系统，
基于真实企业数据，用算法优化仓库作业效率。**

用更好懂的话说：

> **传统仓储系统只负责「把库存记准」；这个项目在此之上，还让系统「自己算」——
> 商品该放哪个位置、拣货员该按什么顺序走，都由算法给出建议。**

**项目类型**：Java + Python 双技术栈的完整业务系统，不是算法 demo，也不是纯 CRUD。
**代码量**：约 11,200 行（Java 5,811 / Vue 3,564 / Python 1,859）。
**核心卖点**：真实企业数据 + 可量化的算法效果 + 并发一致性。

### 1.2 项目要解决的问题

一个仓库每天面临的核心问题是：

| 问题 | 后果 |
|---|---|
| 库存记不准、超卖 | 客户下单了却发不出货 |
| 商品随便放 | 高频商品放在仓库深处，拣货员每天多走很多路 |
| 拣货顺序随意 | 一个订单在仓库里来回跑，效率低 |
| 算法 / 服务出故障 | 业务停摆 |

本项目针对这四类问题**分别给出技术方案**：

| 问题 | 技术方案 | 章节 |
|---|---|---|
| 库存记不准 | 五字段库存模型 + 流水可追溯 | 4.1 |
| 超卖 | 数据库条件更新（判断写进 WHERE） | 4.2 |
| 高频查询压力 | Redis 缓存（Cache-Aside） | 4.3 |
| 拣货路径长 | 四种行业标准策略对比实验 | 4.4 |
| 服务故障导致停摆 | Agent 编排 + 三级降级 | 4.5 |

## 二、系统架构

### 2.1 整体架构

系统由**三个服务**组成：

```
┌─────────────────────────────────────────────────────┐
│              Vue3 管理后台（11 个页面）               │
└──────────────┬──────────────────┬───────────────────┘
               │ /api             │ /agent-api
┌──────────────▼──────────┐  ┌────▼──────────────────┐
│  Java 业务底座           │  │  Python Agent 层       │
│  Spring Boot 3 + MyBatis│  │  FastAPI               │
│  ├ 商品 / 库位 / 库区    │  │  ├ 编排器（路由/校验/降级）│
│  ├ 入库（收货/上架）     │  │  ├ 路径优化（4 种策略）  │
│  ├ 出库（分配/波次/拣货）│  │  └ LLM Agent（查询/解释）│
│  └ 库存（五字段模型）    │  │                        │
└──────────────┬──────────┘  └────┬──────────────────┘
               │                  │
        ┌──────▼──────────────────▼──────┐
        │   MySQL 9（19 张表）+ Redis      │
        └────────────────────────────────┘
```

**三个服务的职责与端口**：

| 服务 | 技术 | 端口 | 职责 |
|---|---|---|---|
| 前端 | Vue3 + Vite | 5173 | 11 个管理页面，通过代理访问两个后端 |
| Java 业务底座 | Spring Boot 3.2 | 8080 | 业务逻辑、事务、数据一致性 |
| Python Agent | FastAPI | 8000 | 算法、编排、LLM 调用 |

**为什么分成两个后端服务？**

Java 负责「**业务**」（事务、数据一致性），Python 负责「**算法**」（路径优化、智能决策）。
这样设计的好处：

- 业务迭代不影响算法，算法调整不动核心交易链路
- 各自用最擅长的技术栈（Java 做企业级业务、Python 做数据处理与算法）
- **如果算法服务挂了，Java 业务底座可以独立运行**——这是三级降级的前提

**服务间如何通信**：**同步 REST 调用**。Java 需要算路径时直接请求 Python，
等结果返回。没有引入消息队列（原因见 2.4）。

**一键启动**：项目提供启动 / 停止脚本，自动探测依赖并依次拉起三个服务。

### 2.2 技术栈与选型理由

| 层 | 技术 | 用在哪 | 为什么选它 |
|---|---|---|---|
| **Java 后端** | Spring Boot 3.2 | 业务底座 | 企业级开发标准，生态成熟 |
| | MyBatis-Plus | 数据持久化 | 单表 CRUD 免写 SQL，复杂查询仍可手写 |
| | MySQL 9 | 19 张表 | 事务与行锁是防超卖的基础 |
| | **Redis** | 库存缓存 | 高频库存查询的旁路缓存 |
| | EasyExcel | 数据导入 / 导出 | 流式读写，内存占用恒定 |
| **Python Agent** | FastAPI | 算法服务 | 异步框架，自动生成接口文档 |
| | Pydantic | 数据校验 | 接口入参出参强类型约束 |
| | PyMySQL + pandas | 数据处理 | 直连数据库 + 数据分析 |
| | **OpenAI SDK** | 调用大模型 | 用通义千问 qwen-plus 实现自然语言查询 |
| **前端** | Vue3 + Vite | 11 个页面 | 组合式 API，开发体验好 |
| | Element Plus | UI 组件库 | 后台管理系统标准选择 |
| | ECharts | 数据可视化 | 看板 / 库位地图 / 路径可视化 |

不需要对象关系映射的复杂度，直接用 PyMySQL 写 SQL 更直观、性能更好。

### 2.3 数据库设计（19 张表）

**表按业务域分 5 组**：

| 业务域 | 表名 | 中文含义 | 作用 |
|---|---|---|---|
| **基础数据**（6） | `product` | 商品款（208） | 鞋款主数据，含 ABC 分类 |
| | `product_sku` | SKU = 款 × 尺码（2,515） | **库存的真正单位** |
| | `warehouse_area` | 库区（18 个） | A ~ R 库区划分 |

| **出库**（6） | `outbound_order` | 出库单（32,621） | 订单头，含状态机 |

| | `picking_wave` | 拣货波次（9,707） | 一批订单合成的一次拣货作业 |
| | `picking_task` | **拣货任务** ★ | 回答「拣货员走哪些库位」，是路径优化的输入 |
| | `shipment` | 发货单 | 发货记录 |
| **库存**（4） | `inventory` | **即时库存（五字段）** ★★ | SKU × 库位的分状态库存，全系统一致性核心 |
| | `inventory_transaction` | **库存流水** ★ | 每次变动留痕，可追溯 + 可对账 |
| | `stocktake_order` / `stocktake_line` | 盘点单 / 明细 | 账面 vs 实盘差异 |
| **其他**（1） | `alert` | 告警表 | 异常类型 / 级别 + LLM 诊断建议 |

#### 四个值得说的设计决策

**① SKU 拆成两张表**

`product`（208 款）1 : N `product_sku`（2,515 个），库存挂 **SKU** 而不是挂款。
这是鞋类 WMS 与普通电商的本质区别——**同一款鞋的不同尺码是独立库存**，
41 码卖光了不代表 42 码也没货。

**② 分配明细与拣货任务分两张表**

| 表 | 视角 | 回答的问题 |
|---|---|---|
| `outbound_allocation` | **订单视角** | 这张订单的货从哪个库位取 |
| `picking_task` | **库位视角** | 拣货员要走哪些库位、各取多少 |

**为什么必须分开**：这是被数据验证过的设计。实测发现
**36.7% 的波次存在同一库位被重复访问**，按库位聚合后**行走次数减少 52%**。
没有 `picking_task` 这张表，路径优化就没有输入。

**③ 库存流水带「来源单据」**

`inventory_transaction` 每条记录都带 `reference_type + reference_id`。
好处有两个：

- **可追溯**：任何一个库存数字，都能查出它是被哪张单据改的
- **可对账**：把流水累加起来，应该等于库存表的数字——不等就说明有问题
  （这个机制真的抓出过 bug，见第六章案例二）

**④ 唯一约束与索引**

- **11 个业务唯一键**：款号、SKU 码、库位码、订单号、波次号……
- **最关键的一个**：`inventory` 表上的 `uk_sku_location(sku_id, location_id)`
  ——保证**一个 SKU 在一个库位只有一条库存记录**，从表结构上杜绝重复行
- **54 个索引**：高频过滤字段（`status`、`created_at`）、所有外键列、
  以及支撑按 SKU × 库位查询的复合索引 `idx_sku_loc(sku_id, location_id)`

#### 两个主动说明的设计取舍

**① 没有使用外键约束**。表之间的关联由**应用层维护**。原因：外键在高并发写入时
会带来额外的锁开销和死锁风险，且不利于后续分库分表。这是互联网业务的常见做法。

**② 没有使用逻辑删除字段**。删除语义统一用**业务状态机**表达：

```
订单状态：  待分配 → 已分配 → 拣货中 → 已发货
分配状态：  0 已分配 / 1 已拣货 / 2 已释放
库位状态：  0 空闲 / 1 占用 / 2 锁定
```

**为什么这样更好**：状态机能表达**「为什么」这个记录不活跃了**
（是拣走了？还是被释放了？），而 `is_deleted = 1` 只能表达「删了」。

## 三、业务功能

### 3.1 三条业务主线

**① 入库：货物进仓库**

```
创建入库单 → 收货（清点数量）→ 上架（系统推荐货位）→ 库存增加
```

**② 出库：货物出仓库**（核心）

```
客户订单 → 分配库存（占住货，防超卖）→ 生成波次 → 拣货 → 发货 → 库存扣减
```

**③ 库存管理**

```
实时查询 / 库存流水（可追溯）/ 冻结解冻 / 库存对账 / 数据导入导出
```

### 3.3 核心流程详解

#### 出库全流程（最核心）

这是本项目最完整、技术含量最高的一条链路，共 6 个环节：

| 环节 | 输入 | 系统做什么 | 输出 |
|---|---|---|---|
| **1. 订单管理** | 客户下单 | 记录订单头 + 明细，生成订单号 | 订单状态 = 待分配 |
| **2. 分配库存** | 订单明细 | 为每个订单行**选定具体库位**，并占用库存（`qty_allocated` 增加） | 分配明细。★ **并发安全的关键点** |
| **3. 波次生成** | 一批订单 | 按容量（27 件）合并成一次拣货作业 | 拣货波次 |
| **4. 拣货任务** | 波次内分配明细 | 按**库位**聚合，生成拣货员视角的取货清单 | 拣货任务。★ **路径优化的输入** |
| **5. 拣货确认** | 拣货员操作 | 库存从「已分配」转为「已拣出」，**总量不变**（货还在仓库） | 库存状态更新 |
| **6. 发货确认** | 出库操作 | 库存**这时才真正扣减** | 库存减少，订单完成 |

**第 5 步的设计要点**：拣货员把货取走了，但货还在仓库里（在拣货车上），
所以**总量 `qty` 不应该减少**，只是状态从「已分配」变成「已拣出」。
只有发货装车了，才真正出库。这符合真实作业。

#### 库存状态流转（五字段如何变化）

以「分配 1 件」为例：

| 时点 | qty（现有） | qty_allocated（已分配） | qty_picked（已拣出） | qty_available（可用） |
|---|---|---|---|---|
| 初始 | 25 | 0 | 0 | 25 |
| 分配后 | 25（不变） | **1** | 0 | **24** |
| 拣货后 | 25（不变） | 0 | **1** | 24 |
| 发货后 | **24**（这时才减） | 0 | 0 | 24 |

**关键**：从分配到最后发货，`qty` 只在发货那一刻减少一次。

## 四、关键技术实现

> **本章是全文档的技术核心，也是简历里最值得写的部分。**
> 所有实测数据都放在对应技术点旁边，便于对照理解。

### 4.1 库存五字段模型

**问题**：库存用「一个数字」表示够不够？

**不够。** 因为库存处在不同的状态中：有的被订单占住了、有的正在被拣货员取走、
有的因为质检不合格被冻住了……用一个数字无法表达这些区别。

**本项目的设计**：库存表用**五个数量字段**分别记录不同状态。

| 字段 | 含义 | 生活类比 |
|---|---|---|
| `qty` | 现有总量 | 冰箱里一共有 10 瓶牛奶 |
| `qty_allocated` | 已分配给订单 | 其中 3 瓶已被订单预定，别人不能拿 |
| `qty_picked` | 已拣出未发货 | 2 瓶已拿在手上，还没出库 |
| `qty_onhold` | 冻结 | 1 瓶发现过期，锁住不能动 |
| `qty_available` | **可用量** = 总量 − 已分配 − 冻结 | **实际还能卖的 = 4 瓶** |

**为什么必须这么设计**（三个理由）：

1. **防超卖**：订单必须先「占住」库存（`allocated`），别人就不能再卖
2. **符合真实作业**：拣货员取走货但还没发货时，库存「总数」不应减少（货还在仓库）
3. **异常可表达**：质检不合格的货要「冻住」，与正常订单占用**必须分开**——
   因为这是两种性质完全不同的占用，混在一起就无法区分「被订单占了」和「被冻结了」

> **这是全项目最核心的一个设计**。面试时如果只能讲一个技术点，讲这个。

### 4.2 并发扣减防超卖（含压测方法论）

**问题**：多个订单同时抢同一批库存，如何保证不超卖？

**超卖是怎么发生的**：库存只剩 1 件，两个订单同时下单，两个请求都读到「有 1 件」，
各自判断「够」，各自扣减，最终卖了 2 件，库存变成 −1。
**本质是「读取 → 判断 → 扣减」这三步不是原子的。**

#### 解法：把判断写进 WHERE 条件

```sql
UPDATE inventory
SET qty_allocated = qty_allocated + #{qty},
    qty_available = qty_available - #{qty}
WHERE sku_id = #{skuId}
  AND location_id = #{locationId}
  AND qty_available >= #{qty}      -- ★ 把"够不够"写进 WHERE 条件
```

**为什么这样就安全**：

- 数据库在执行这条 UPDATE 时会**对该行加锁**
- 「判断库存够不够」和「扣减库存」变成了**一个不可分割的操作**
- 两个并发请求会**排队执行**：第一个扣完，第二个再判断时发现不够，直接失败
- 返回影响行数：**1 = 成功，0 = 库存不足**（Service 层抛异常触发事务回滚）

#### 压测方法论（怎么证明它真的不超卖）

**这不是"跑个压测看数字"，而是有设计的实验。**

**被测目标**：`POST /api/outbound-orders/{orderId}/allocate`（订单级库存分配，整单原子）

**测试工具**：自己写的 Python 压测脚本，可命令行复跑。三个关键设计：

1. 用 `ThreadPoolExecutor` 线程池**打真实 HTTP 接口**（不是直接调方法，避免绕过 Web 层）
2. 用 `subprocess` 调 mysql 命令**从数据库侧独立校验**最终库存
   （不信任接口返回，直接查库，避免"接口说成功但库里没扣"）
3. 测试前先把该 SKU 库存**清零再置为目标值**，保证每次起点确定

#### 场景设计：为什么是 100 / 50 / 20 / 10

固定「每个订单只要 1 件」，通过**逐级缩小库存来制造越来越极端的争抢**：

| 场景 | 库存 | 并发订单 | 并发线程 | 争抢倍数 |
|---|---|---|---|---|
| 1 | 100 | 225 | 100 | 2.25× |
| 2 | 50 | 204 | 200 | 4.08× |
| 3 | 20 | 185 | 180 | 9.25× |
| 4 | 10 | 156 | 150 | **15.6×** |

> **一个体现实验严谨性的细节**：候选订单**只挑选「只有一行、且数量为 1」的订单**。
> 因为分配是**整单原子**的——多行订单的失败可能来自其它 SKU 库存不足，
> 会污染结论，让你误判成超卖。这个细节保证了实验结论的有效性。

#### 压测结果

**正确性判定（4 项全部通过）**：

| 场景 | 库存 | 并发订单 | 成功 | 失败 | 最终库存 | 判定 |
|---|---|---|---|---|---|---|
| 1 | 100 | 225 | **100** | 125 | 100 | ✅ |
| 2 | 50 | 204 | **50** | 154 | 50 | ✅ |
| 3 | 20 | 185 | **20** | 165 | 20 | ✅ |
| 4 | 10 | 156 | **10** | 146 | 10 | ✅ |

**每个场景「成功订单数恰好等于库存数」**，说明零超卖。

判定标准（4 项同时满足才算通过）：
1. 已分配量 == 库存量
2. 成功订单数 == 库存量
3. `qty >= 0`（从未变负）
4. 库存被精确扣减

**性能数据**：

| 指标 | 范围 |
|---|---|
| QPS | **436 ~ 908** |
| P50 延迟 | 43 ~ 186 ms |
| P95 延迟 | — |
| P99 延迟 | **80 ~ 374 ms** |

> **一个有意思的现象**：库存越小，QPS 反而越高（436 → 908）。
> 因为库存少时大部分请求很快就失败了（不用等锁），平均耗时反而降低。

### 4.3 Redis 缓存

**问题**：出库前每次都要查「这个商品还有多少可用库存」，
这是个高频查询，会给数据库造成持续压力。

#### 解法：Cache-Aside（旁路缓存）模式

```
读：先查缓存 → 命中直接返回
             → 未命中 → 查数据库 → 把结果写回缓存

写：更新数据库 → 删除缓存（而不是更新缓存）
```

**为什么「写的时候删缓存」而不是「更新缓存」**：

更新缓存有并发顺序问题——两个请求先后更新数据库和缓存，如果顺序错乱，
缓存里会留下旧值。**删除缓存则让下次读自然回源**，更简单也更可靠。
（这是业界公认的 Cache-Aside 最佳实践）

#### 三个经典缓存问题的应对

| 问题 | 现象 | 本项目的做法 |
|---|---|---|
| **缓存穿透** | 查询不存在的数据，每次都打数据库 | 空结果也缓存（但过期时间设短） |
| **缓存雪崩** | 大量缓存同时过期，数据库被瞬时打垮 | 过期时间加**随机偏移**，避免同时失效 |
| **缓存击穿** | 热点数据过期的瞬间，大量请求同时回源 | **本场景数据量小、回源快，不处理**（有意识的取舍） |

#### 一个容易被忽略的细节：事务提交后才删缓存

**如果直接在事务里删缓存，会出现这样的问题**：

```
时间线：
T1: 更新数据库（还没提交）→ 删除缓存
T2: 读缓存发现没有 → 读数据库（此时看到的是旧值）→ 把旧值写回缓存
T1: 事务提交（数据库已经是新值）
结果：缓存里是旧值，与数据库不一致 ❌
```

**本项目的解法**：用 Spring 的 `TransactionSynchronization` 机制，
**在事务提交之后**才执行删缓存。上述窗口就不存在了。

> 这个细节很多项目都会踩坑，能讲清楚说明对「数据库事务」和「缓存」的
> 交互边界有真实理解。

#### 实测效果

服务端在响应里回传了本次查询的实际耗时，实测三种情况：

| 场景 | 服务端耗时 |
|---|---|
| 首次请求（含 JVM / 连接池冷启动） | 592 ms |
| 稳态查询（缓存未命中，回源数据库） | **2 ~ 3 ms** |
| 缓存命中 | **0 ~ 1 ms**（计时器精度 1ms，即亚毫秒级） |
| 库存变动后 | 缓存自动清除，再查拿到新值 ✅ |

> **为什么要把「首次」和「稳态」分开**：592ms 是服务刚启动时的**一次性开销**
> （JVM 预热、连接池初始化、首次查询计划生成），不是数据库查询的常态。
> **真正反映缓存收益的是稳态对比：2~3ms → 亚毫秒**。
> 如果拿冷启动的 592ms 去和缓存命中比，会把收益夸大两个数量级——
> 这种数字经不起追问，所以我按实际口径分开列。

### 4.4 拣货路径优化（含 100 波次批量实验）

**问题**：一个拣货波次包含多个货位，拣货员按什么顺序走最省力？

#### 第一步：确定仓库布局

数据集自带 **CAD 总图 + 四张分层平面图**，配套论文
（*Data in Brief* 61, 111837, 2025）给出了明确的布局参数：

| 参数 | 值 |
|---|---|
| 纵向横通道（vertical aisles） | **3 条**，x = 66 / 403 / 686，中间那条是 **central cross aisle** |
| 横向拣货通道（parallel sorting aisles） | **17 条** |
| 货架 | 双面货架（double-sided），共 25 个 |
| 层数 | 4 层（两个拣货层 + 两个补货层） |
| 每个货位容量 | 18 个商品 |

结合导航点数据（44 个点，**每条通道 17 个 y 值，三列完全一致**）还原出俯视结构：

```
        ┌──────────────────────────────────────┐
        │ ▬▬▬▬▬▬▬▬   ▬▬▬▬▬▬▬▬   ← 货架排（横向）  │  ↑ y
        │ ─────────  ─────────   ← 拣货通道      │
        │ ▬▬▬▬▬▬▬▬   ▬▬▬▬▬▬▬▬                  │
        │ ─────────  ─────────                  │
        └──┬──────────┬──────────┬──────────────┘
           x=66      x=403      x=686        → x
         左横通道   中央横通道   右横通道
```

**三条纵向横通道把仓库分成左右两个区块**——这是仓储运筹学里标准的
**多区块（multi-block）布局**，中间那条横通道即论文所说的 central cross aisle。

> ⚠️ **这里最容易搞反**：拣货员是**沿横向拣货通道走（x 方向）**，
> 经**纵向横通道（x=66/403/686）换道**。我第一版就把它理解成了
> "3 条纵向拣货通道 + 两端横通道"，方向正好差了 90°。

#### 第二步：建立统一的距离模型

四种策略必须用同一个口径：

```
沿横向拣货通道走（x 方向）  +  经纵向横通道换道（y 方向）
        ★ 换道只能走 x=66 / 403 / 686 这三条纵向横通道（不能穿货架）
取货距离 = |货位 y − 所属拣货通道 y|（每个货位固定，与拣货顺序无关）
```

**三条换道规则**：

1. **同一条拣货通道内**：直接沿 x 走，`|Δx|`
2. **换拣货通道**：必须经某条纵向横通道，取最省的那条：
   `min over c∈{66,403,686} of |x₁−c| + |x₂−c| + |Δy|`
3. **取货**：从通道走到货位，距离 = `|货位 y − 通道 y|`（每个货位固定，
   与顺序无关，是个常数项）

#### 第三步：实现四种行业标准策略

| 策略 | 出处 | 核心思想 |
|---|---|---|
| **顺序拣货（基线）** | 复现原系统做法 | 按订单顺序机械组合，不做优化 |
| **返回式（Return）** | Hall (1993) | 每条通道从同一端进、取完**原路返回** |
| **S形（S-shape）** | Hall (1993) | 蛇形穿越，**通道内单向走到底**不回头 |
| **最大间隙（Largest Gap）** | Hall (1993) | 通道内**最大的空隙段完全不走** |

**最大间隙是四种里最巧的**：它把拣货通道看成一条线段，找出相邻取货点之间
（含通道两端）的最大空隙，以它为界把通道切成左右两段：

```
|  左段（从左端进）  |  ← 最大空隙，不走 →  |  右段（从右端进）  |
入口↓                                         入口↑
```

**那一段空隙自始至终不踏入**——这才是它省距离的地方。因为一条通道要从两端
各进一次，整条路线必须组织成「左端 → 整条穿过一条通道到中央 → 中央 →
整条穿过一条通道到右端 → 右端 → 整条穿过一条通道回左端」的回路。

#### 第三步补：让策略真正用上中央横通道

写完第一版后我发现一个**实现上的真问题**：

论文说明仓库有 **3 条**纵向横通道，但我实现的返回式和 S形**只在两端
（x=66 和 x=686）进出，中间那条 403 完全没用到**——等于白扔了一条基础设施。

而中央横通道的作用很大：**左右两个区块的货位都可以从它进出**，
不用每次都从最左端一路走到最右端。

于是我按**区块分段**重写了三种策略：

| 策略 | 改动 |
|---|---|
| **返回式** | 按「通道 × 区块段」处理，每一段可以从 66 / 403 / 686 任一端进出，取最近的那端 |
| **S形** | 分左右两个区块各自扫一遍，段内在两端之间单向走满 |
| **最大间隙** | 每段独立找最大空隙；整条路线组织成「左端 → 中央 → 右端 → 回左端」三阶段 |

**这一步的意义不只是"数字更好看"**——它让三种策略**建立在同一套基础设施上**，
比较才公平。否则最大间隙赢，可能只是因为别人被"绑住了一只手"。

**效果**（同一批 100 波次）：最大间隙离理论最优从 **16.7% 降到 10.7%**，
平均节省从 16.1% 升到 **23.7%**。

#### 第四步：批量实验（100 个真实波次）

**抽样规则（固定可复现）**：取任务数 3~25 的波次共 **8,393 个**，
按 `wave_id` 升序**等间隔抽取 100 个**——不用随机数，任何人重跑都得到同一批。

**总体结果**：

| 策略 | 平均距离 | 相对基线 | 胜出次数 |
|---|---|---|---|
| 顺序拣货（基线） | 7,064 米 | — | 13 / 100 |
| 返回式 | 5,735 米 | −18.8% | 9 / 100 |
| S形 | 6,184 米 | −12.5% | 1 / 100 |
| **最大间隙** | **5,101 米** | **−27.8%** | **77 / 100** |

**每波取最优策略，平均节省 23.7%（中位数 27.9%，区间 0% ~ 50.9%）。**

#### 第五步：用精确最优解做基准

只看「谁比谁好」还不够。文献里衡量启发式的方法是**看它离理论最优差多少**，
所以我用 **Held-Karp 动态规划**求出了理论最短路径（任务数 ≤12 时精确可解）：

| 策略 | 平均高于最优 |
|---|---|
| 顺序拣货（基线） | 17.6% |
| 返回式 | 13.0% |
| S形 | 20.9% |
| **最大间隙** | **10.7%** |

**与文献对照**（据 Wäscher 领域综述转述的原始数据）：

- **Petersen (1997)**，随机存储：最大间隙与 composite 平均约高于最优 **9~10%**
- **Petersen & Schmenner (1999)**，频率存储：最大间隙 **7.1%**、composite 10.2%、
  midpoint 12.0%；返回式 **27.9%**、穿越式（S形）**30.9%**

**排序一致** ✅ —— 文献与实验都是「**最大间隙最优、S形最差**」。

**最大间隙的绝对差距也与文献一致**（**10.7%** vs 文献 7~10%）✅
返回式（13.0%）与 S形（20.9%）甚至优于文献水平（27.9% / 30.9%）。

> 原因是**基础设施不同**：本仓库有 **3 条纵向横通道**（两端 + 中央），
> 三个位置都能进出拣货通道；文献中的仓库通常只有两端。
> **通道数不同，绝对数字不能逐条对齐，能对齐的是排序。**

> **引用的文献**：Hall, R.W. (1993), *IIE Transactions* 25(4)；
> Petersen, C.G. (1997), *IJOPM* 17(11)；
> Petersen, C.G. & Schmenner, R.W. (1999), *Decision Sciences* 30(2)；
> Ratliff, H.D. & Rosenthal, A.S. (1983), *Operations Research* 31(3)；
> Wäscher, G. (2002), 工作论文 13/2002, 马格德堡大学（领域综述）；
> de Assis, R.F. et al. (2025), *Data in Brief* 61, 111837（本数据集论文）。

#### 结论

本仓库是**多区块布局**（17 条拣货通道 + 3 条纵向横通道 + 中央横通道），
拣货单较短（中位 16 件，落在 Petersen 给出的「≤25 件时最大间隙最优」区间内），
文献预测**最大间隙在此条件下占优**——实验结论吻合：它**胜出 77/100**，
且离最优最近（**10.7%**，正落在文献的 9~10% 区间内）。

> 返回式（13.0%）和 S形（20.9%）甚至**优于**文献水平（27.9% / 30.9%）。
> 原因是**基础设施不同**：本仓库有 3 条纵向横通道，两端与中央都能进出；
> 文献中的仓库通常只有两端。**通道数不同，绝对数字不能逐条对齐，能对齐的是排序。**

**而这个过程本身更能说明问题**：我前后走过两段弯路——

1. **第一版**：取货后位置重复计数、换通道按直线距离算 →
   算出「最大间隙一次都没赢」，**与文献结论完全相反**
2. **第二版**：把通道方向搞反了（当成 3 条纵向拣货通道 + 两端横通道），
   把"沿通道走的距离"误当成"进架取货深度" → 收益率虚高一倍以上

**两次都是「算出来的结论和文献/常识对不上」逼我回头查模型。**
最后我拿到了数据集自带论文与官方 CAD 布局图，把仓库结构彻底核实，
重写距离模型；**又发现实现上没利用中央横通道，三种策略按区块分段重做了一遍**。

全程做了三重校验：**换道必须发生在横通道上**（物理合法性）、
四种策略的拣货序列**不重不漏**、精确最优解**不差于任何启发式**。

### 4.5 Agent 编排与三级降级

**问题**：算法服务可能因各种原因不可用（超时、异常、结果不合法），
不能因为算法挂了就让业务停摆。

#### 编排器的四个职责

1. **任务路由**：按任务类型分发给对应模块（**确定性逻辑，不是让 AI 自由决定**）
2. **上下文管理**：统一组装各模块需要的输入，避免重复查数据库
3. **结果校验**：算法输出必须检查合法性，**不能盲信**
4. **降级决策**：失败时切换到备用方案

#### 三级降级管线

```
① 算法正常        → 成功（最优结果）
② 规则桩兜底      → 降级（结果质量下降，但业务可用）
③ 都失败          → 失败（生成人工工单）
```

**「规则桩」是什么**：每个决策模块都有一个「最简单的备用规则」，保证一定算得出来：

| 模块 | 规则桩 |
|---|---|
| 路径优化 | 按库位编码顺序拣货 |
| 需求预测 | 最近 7 天移动平均 |
| 货位分配 | ABC 分类就近 |
| 异常诊断 | 按类型返回预置文案 |

#### 故障注入测试（验证降级真的生效）

我**主动注入故障**来验证降级链路是否真的工作，而不是只写在文档里：

| 注入的故障 | 结果 |
|---|---|
| 算法异常（请求不存在的波次） | ✅ **降级**，规则桩接管，业务不中断 |
| 参数非法（错误的策略名） | ✅ **降级** |
| 未知任务类型 | ❌ 失败（正确行为，需人工处理） |
| 正常任务（对照组） | ✅ 成功（28 ms） |

**并且做了监控面板**，可以实时看到**降级率**——
这证明降级设计是「真在运行、可观测」的，而不是纸面设计。

#### LLM 用在哪、不用在哪（同样是有意识的取舍）

| 场景 | 用什么 | 为什么 |
|---|---|---|
| 预测 / 货位 / 路径 | ❌ **不用 LLM** | 要可解释、可复现、可验证，LLM 做不到 |
| 异常**检测** | ❌ 用统计规则 | 确定性方法，不该交给概率模型 |
| 异常**解释** | ✅ **用 LLM** | 把异常数据翻译成人话，是 LLM 的强项 |
| **自然语言查询** | ✅ **用 LLM** | 理解中文提问 → 调用工具查数据 → 组织回答 |

#### 自然语言查询的实际效果

用户用中文直接问系统：

```
问：仓库现在有多少库存？
答：当前仓库总库存为 125,976 件。

问：8N10W9-11 这个 SKU 分布在哪些库位？
答：分布在 Q-13-13（34 件）/ M-01-30（32 件）/ P-06-12（32 件）

问：哪些拣货员作业量最少？
答：作业量最少的拣货员是 Operator_21，仅完成 2 波次作业。
```

**技术原理**：LLM **不直接算数**——它只负责「理解意图，决定调用哪个工具」，
数据由系统查数据库获得，最后 LLM 把结构化数据组织成自然语言。
这避免了 LLM 编造数字的问题。

### 4.6 数据导入导出

这两个功能不在最初的规划里，是开发中**主动增加**的——因为真实 WMS 上线时，
期初数据（商品、库位、库存）就是通过 Excel 批量导入的。

#### 数据导入

| 特性 | 说明 |
|---|---|
| 导入对象 | 商品 / 库位 / 期初库存三类 Excel |
| 校验 | **逐行校验**，错误行给出具体原因（哪一行、哪个字段、什么错） |
| 错误处理 | 错误明细汇总返回，**不中断整个导入**，正确行照常入库 |
| 模板下载 | 提供标准模板，避免用户自己猜格式 |

#### 数据导出

| 特性 | 说明 |
|---|---|
| 导出对象 | 库存 / 订单 / 拣货单 |
| 实现方式 | **分批查询 + 流式写入**（每批 500 条，查完立即写入 Excel） |
| 内存特性 | **内存占用恒定**，不随导出行数增长 |
| 安全上限 | 10 万行，防止误操作导出全表拖垮服务 |

**为什么是「分批流式」而不是「一次查完再写」**：这不是性能优化，
而是**正确性的必然选择**——一次性把 3 万条查进内存本身就是错的，
数据量再大就会内存溢出。这个决策背后的完整排查过程见第六章案例一。

## 五、数据处理与质量

> **这一章体现的是「数据工程」能力**——拿到一份真实的、脏的原始数据，
> 怎么把它变成能支撑业务系统的干净数据。

### 5.1 从原始 CSV 到数据库

原始数据是 7 个 CSV 文件（分隔符还不统一，有的逗号有的分号）。
要让它们变成 19 张表里的业务数据，经过了一条完整的数据处理链路：

| 步骤 | 做什么 | 结果 |
|---|---|---|
| **1. 全字段数据体检** | 逐字段核对类型 / 范围 / 空值 / 唯一性 | 发现 7 个数据问题（见 5.2） |
| **2. 尺码字段还原** | `size > 20` 则除以 10，修复小数点丢失 | 尺码恢复为合理范围 1.0 ~ 30.5 |
| **3. 无效订单行过滤** | 只保留 `quantity > 0` 且尺码非空的行 | 122,370 → 122,321 行（−49） |
| **4. 库位表补全** | 补 6 个缺失标准库位 + 16 个功能区库位 | 2,292 → **2,314** 个 |
| **5. 库位类型推断** | 按「是否被拣过」判定存储区 / 拣货区 | 584 存储区 / 1,730 拣货区 |
| **6. 异常波次保守处理** | 77 个「有订单无波次记录」的波次号：保留订单，不生成拣货任务 | 不丢数据，也不造错误任务 |
| **7. 维度表构建与去重** | 从事实表提取维度 | 商品 208 / SKU 2,515 / 库区 18 / 客户 588 / 拣货员 24 |
| **8. 出库明细合并** | 同订单同 SKU 的多行合并 | 得 `outbound_order_line` 115,654 行 |
| **9. 拣货任务聚合** | 原始行按「波次 × SKU × 库位」聚合 | 215,192 行 → `picking_task` **112,977** 行 |
| **10. 脚本化导入** | 生成 SQL 脚本而非手工导入 | 19 张表，分 3 个脚本文件 |
| **11. 入库后验证** | 数据量核对、悬空引用检查、汇总与明细一致性、抽样核对 | 全部通过 |

**两个值得单独说的步骤**：

**第 9 步（拣货任务聚合）为什么重要**：
原始数据里同一个库位在一个波次内可能被访问多次。
实测 **36.7% 的波次存在重复访问**，按「波次 × SKU × 库位」聚合后
**行走次数减少 52%**。这不只是数据整理，而是直接决定了路径优化的输入质量。

**第 11 步（入库后验证）为什么必须有**：
数据导入最容易出的问题是「看起来导进去了，其实有悬空引用或对不上」。
所以导入后做了四层验证：数据量核对、7 类关系悬空引用检查（结果 0 个）、
波次汇总与明细一致性、随机抽样人工核对。

### 5.2 数据质量问题与处理

全字段体检一共发现 **7 个问题**，这里详述技术含量最高的 3 个。

#### 问题 1（最严重）：尺码字段存在两种格式混用

**现象**：尺码取值范围是 **1.0 ~ 305.0**——鞋码不可能到 305。
其中大于 20 的记录有 **41,549 条（占 34%）**，涉及 **15,592 个订单（占 48%）**。

取值分布呈现明显的两段：

```
75, 85, 95, 105, 115, 125          （间隔 10）
215, 220, 225, 230, ... 305        （间隔 5）
```

**根因**：**数据导出时小数点丢失**。同一个字段里混用了 `8.5` 和 `85` 两种格式。

**处理方式**：**不删除、不置空，而是还原**：

```
size_real = size_raw / 10   if size_raw > 20
          = size_raw        否则
```

**为什么敢这么处理——三重证据验证**（这一步很关键，不能凭感觉改数据）：

1. 还原后尺码变成 1.0 ~ 30.5 的合理序列，且**取值种数不变**（都是 45 种）——
   说明是双射变换，没有信息损失
2. 单个商品的尺码还原后成为**连续序列**（如某款为 7, 7.5, 8, ..., 13）
3. **SKU 总数仍是 2,515，同款同码冲突 0 个**——证明还原后没有产生碰撞

#### 问题 2：无效订单行

**现象**：`quantity = 0` 有 33 条；尺码为 NULL 有 16 条。

**根因**：订单行没有数量，或无法定位到具体 SKU，**没有业务意义**。
NULL 行多为源系统录入缺失。

**处理**：导入时过滤 `WHERE quantity > 0 AND size IS NOT NULL`，
合计过滤 49 行（122,370 → 122,321）。
**注意：过滤的是订单「行」，没有删除任何订单**——除非该订单的全部行都无效。

#### 问题 3：库位表不完整

**现象**：两处缺失

- 波次数据用到的 **6 个标准库位**在库位表里不存在
  （E-25-20、G-25-10、I-25-20、J-25-20、K-25-20、K-26-20）
- 有 **16 个非标准编码的功能区**（RC-01~05 收货区、EX-01/04/11 发货区、
  C-0xx 中转区、ZN-COR 角落区）也不在库位表里

**根因**：源库位表只导出了标准储位，功能区与部分储位未导出。

**处理**：**从 2,292 个已有库位反推编码规律**——
库位号 `区-排-列` 中，`列 → (x, z)`、`(区, 排) → y`，
在 300 个组合上验证**零冲突**，据此推算出 6 个缺失库位的坐标。
16 个功能区全部建为正式库位并赋予 `location_type`。

**这是「推断」而非「真实」数据，已在数据真实性分级中如实标注。**

#### 其余 4 个问题（均已处理，影响较小）

| 问题 | 现象 | 处理 |
|---|---|---|
| 问题 4 | 77 个波次号「订单表有、波次表无」（订单表 9,784 vs 波次表 9,707） | 保留订单，不生成拣货任务 |
| 问题 5 | `K-23-30` 与 `K-23-40` 坐标完全相同（疑 z 值录入错） | 保留原样，仅地图上两点重叠 |
| 问题 6 | `sector` 字段全部为同一值，无信息量 | 不参与业务 |
| 问题 7 | 波次容量超标（74 个波次超过论文所述 27 件上限） | 保留原样，算法约束以实际数据为准 |

### 5.3 从数据里发现的业务规律

> 这些不是「跑个统计」，而是**发现了能指导系统设计的规律**。
> 老师如果问「你从数据里看出了什么」，这几条就是答案。

#### 发现一：48% 的库位从未被拣货使用

| 库区 | 库位数 | 使用率 |
|---|---|---|
| A ~ G 区 | 580 | **0%（完全闲置）** |
| H 区 | 88 | 35% |
| I ~ R 区 | 1,404 | 54% ~ 76% |

**业务含义**：真实仓库存在明确的**储备区 vs 拣货区**分工——
A~G 区离通道远或位置偏，只用于长期存储，日常拣货不会去那里。

**对系统的指导**：据此给库位增加了 `location_type` 字段
（584 个存储区 / 1,730 个拣货区），这是**货位分配算法的基础**。

#### 发现二：21% 的商品贡献 41% 的作业量

| 分类 | 款数 | 占比 | 拣货次数占比 | 平均拣货次数 |
|---|---|---|---|---|
| A 类 | 44 | 21.2% | **40.7%** | 1,990 次 |
| B 类 | 70 | 29.3% | — | 902 次 |
| C 类 | 94 | 30.0% | — | 686 次 |

**A 类的平均拣货次数是 C 类的 2.9 倍**——这验证了企业 ABC 分类的有效性，
也说明**高频商品应该放在靠近通道的位置**。

**对系统的指导**：这正是「货位分配优化」功能的理论依据。

#### 发现三：同一库位在一个波次内被重复访问

**36.7% 的波次存在同库位重复访问**——拣货员在一个波次里会多次走到同一个货位。

**对系统的指导**：这是 `picking_task` 表按「波次 × SKU × 库位」聚合的设计依据，
聚合后**行走次数减少 52%**。**一个数据发现，直接改变了一张表的设计。**

#### 发现四：`RC-01` 是特殊商品专属区

`RC-01` 被拣 22,979 次（全场最高，占总拣货 10.7%），
其中单个商品 `PY5UPB` 就占了 12,063 次（52%）。
而该商品总拣货 13,380 次，**90% 都发生在 `RC-01`**。

对照普通商品 `8N10W9`：拣货 18,069 次，却分散在 **62 个库位**。

**业务含义**：真实仓库对**特殊商品（该款是大码鞋，尺码 21.5~30.5）单独划区管理**。
这是从数据里「读」出来的仓库管理经验。

## 六、工程实践：三个真实排查案例

> 这一章记录我在开发中遇到的真实问题。
> **每个案例的重点都不是「我修了个 bug」，而是「我怎么定位和决策」。**

### 案例一：导出 3.2 万条订单，Excel 里只有 500 行

**现象**：开发数据导出功能时，导出 3.2 万条订单，结果 Excel 里**只有 500 行**。
而导出代码里明明写的是 `pageSize = 50000`。数字对不上，且没有任何报错。

**排查过程**：搜索代码里所有的 `500`，发现**两层独立的上限同时在生效**：

1. `PageQuery` 的 getter 里有 `pageSize > 500 ? 500 : pageSize` 的防御式截断
2. MyBatis-Plus 分页插件配置了 `page.setMaxLimit(500L)`

两处都是为保护**列表接口**（防止前端一次拉太多数据）而设的，
却把**导出功能**一起卡死了。

**关键决策：我没有把上限调大。**

第一反应是「把 500 改成 50000 不就行了」——但这是错的。
**一次性把 3 万条数据查进内存本身就是错的**，
数据量再大 10 倍，直接内存溢出，而且 GC 会非常频繁。

**正确解法：换一条不依赖大 pageSize 的路径**

```
每批查 500 条 → 立即写入 Excel → 再查下一批 → ... → 直到查空页 → 收尾
```

- 复用现有的分页查询逻辑，**不动列表接口的保护措施**
- 内存占用**恒定**（永远是 500 条的大小），数据量再大也不会出问题
- 另外加了 **10 万行安全上限**，防止误操作导出全表拖垮服务

**这个案例体现了什么**：面对一个「看起来改个数字就行」的问题，
**拒绝了显而易见但错误的解法**，选择了需要多写代码但正确的方案。
并且补了防护措施（安全上限），而不是修完就走。

### 案例二：库存对账功能抓出 8 条数据不一致

**这个案例的特别之处**：**不是我写错了一个 bug，而是我做的校验功能
真的抓出了数据不一致。** 叙事方向是反的。

**背景**：我做了「库存对账」功能——把库存流水的变动累加起来，
和库存表里的数字比对，不一致就报出来。

**现象**：对账功能报出 **8 条不一致**，例如：

```
56TC1Z-11 @ L-04-23：库存表 = 49，流水累计 = 48，差异 = 1
```

**排查过程**：对账口径是 `inventory.qty == SUM(流水.qty_delta)`。
回溯操作顺序后发现：

1. **先做了发货测试**（库存 50 → 49）
2. **之后才生成期初流水**——于是期初流水按「当时的库存」记为 49
3. 再叠加发货的 −1，流水累计 = 48
4. 而库存表仍是 49 → **差异 1**

**根因**：**期初快照与后续变动发生了时序交错**。
期初流水本应记录「最开始的干净值」，却被在做过业务操作之后才生成，
记成了操作后的值。

**解法**：按正确顺序重新初始化：

```
清空 → 生成库存 → 立即生成期初流水（此时是干净初始值）→ 对账通过 ✅
```

**这个案例体现了什么**：

- **主动设计了数据一致性校验机制**，而不是被动等 bug 暴露
- 这个校验的结论可以推广：**以后任何人直接改数据库而不记流水，这个功能立刻能发现**
- 属于**数据正确性 / 审计**层面的思考，超出了普通 CRUD

### 案例三：代理前缀与前端路由撞车，页面被代理吞掉

**现象**：访问 `http://localhost:5173/agent`，
显示的却是 `{"detail":"Not Found"}`——一段 JSON，而不是 Vue 页面。

**根因**：`vite.config.js` 里配置了 `/api → :8080` 和 `/agent → :8000` 两个代理，
而前端路由里恰好也有一个叫 `/agent` 的页面。

**Vite 代理的匹配优先级高于前端路由**，请求先被代理转发到了 Python 服务，
而 Python 侧没有 `/agent` 这个路径 → 返回 404。

**解法**：代理前缀改名为 `/agent-api` 并配置 `rewrite` 去掉前缀，
前端请求的 baseURL 同步改为 `/agent-api`。

**这个案例最有价值的是那句判据**：

> **返回的是 JSON 而不是 HTML，说明请求根本没到前端，被代理转走了。**

一步就能定性问题出在哪一层，不用去翻前端代码。
结论也沉淀成了项目约定：**代理前缀统一带后缀（`/api`、`/agent-api`），
前端路由用业务名**，从命名上避免再次撞车。

| **难点** | 增删改查 | **并发一致性** + **算法优化** |
| **成果** | 功能多 | **可量化**（零超卖、路径平均省 23.7%、缓存命中亚毫秒） |
| **工程** | 写完即可 | **有实测数据支撑、有降级设计、有数据校验机制** |
| **取舍** | 技术越多越好 | **知道哪里该用 LLM、哪里不该**（见 4.5 节） |

### 7.2 体现的能力

**技术深度**

- 并发控制（条件更新防超卖，有压测验证）
- 缓存一致性（Cache-Aside + 事务提交后删缓存）
- 数据库设计（五字段库存模型、19 张表、11 个唯一键）
- 算法优化（路径优化对标 4 种行业标准策略 + 精确最优解，100 波次批量实验）

**数据工程**

- 从脏的原始数据到可用业务数据，完整的清洗与验证链路
- 发现 7 个数据质量问题并逐个给出有依据的处理方案
- 从数据里读出业务规律，并据此改进系统设计

**工程思维**

- 接口先行、规则兜底、降级设计、数据对账
- 问题排查有方法（案例三那句判据）
- 做完功能补护栏（导出的 10 万行上限）

**判断力**

- **知道什么时候不该用某技术**：数值决策不用 LLM 而用确定性算法（4.5 节），
  缓存击穿在本场景下不做处理（4.3 节）——都是判断，不是遗漏

> **最后一点尤其值得在简历和面试中体现**：
> 面试官更看重「你为什么这么做」，而不是「你用了多少技术」。
