| 货位分配优化 | ⬜ 未实现（原因见下） |
| 编排器 + 降级 | ✅ 完成 |
| 自然语言查询 / 异常解释 | ✅ 完成（LLM） |
| 首页看板 / 库位地图 | ✅ 完成 |

**关于「货位分配优化」为什么没做**：
数据集自带的 `Class_Based_Storage` 就是「按 ABC 摆」的方案。
如果我们的算法只是「按 ABC 摆」，那只是**复现基准之一，没有增量**。
要做出价值必须超过 ABC（如加入商品关联度、容量约束优化），
在时间有限的情况下，**优先做了 JD 明确要求的「调度编排 + LLM Agent」**。

**砍掉的核心原则**：**做深两个算法，而不是堆 30 个浅功能。**

## 二、逐模块功能

### 1. 基础数据（2 个）

| # | 功能 | 说明 | 数据 | 标记 |
|---|---|---|---|---|
| 1.1 | 商品管理 | 款（208）+ 尺码（45）两级，SKU = 2,515；支持列表/查询/详情 | ✅ 真实 | 🔴 |

> 客户（588）和拣货员（24）**不做独立模块**，仅作为订单/波次上的字段展示。

### 1.5 数据管理（2 个）★ 开发中新增

| # | 功能 | 说明 | 标记 |
|---|---|---|---|
| 1.5.1 | **数据导入** | 商品 / 库位 / 期初库存 Excel 导入<br>· 模板下载　　 · 逐行校验　　 · 错误明细反馈 | ✅ |
| 1.5.2 | **数据导出** | 库存 / 订单 / 拣货单导出<br>· **分批查询 + 流式写入**（内存恒定）<br>· 10 万行安全上限 | ✅ |

> **为什么加这两个**：对应真实 WMS 的上线流程——
> 系统本身是空的，要靠「期初盘点导入」把历史数据灌进去才能运转。
> 这也是对「系统没有数据」这个质疑的正面回应：**不是系统没数据，是数据靠导入而来。**

### 2. 入库（3 个）

| # | 功能 | 说明 | 数据 | 标记 |
|---|---|---|---|---|
| 2.1 | 入库单 | 单头 + 明细（款/码/计划数量）；列表/创建/详情 | ⚠️ 构造 | 🔴 |
| 2.2 | 收货 | 填实收数量，明细状态 → 已收货 | ⚠️ 构造 | 🔴 |
| 2.3 | 上架 | 系统推荐货位 → 确认 → 库存 +N | ⚠️ 构造 | 🔴 |

> **不做审核步骤**（简化）。入库量由补货建议驱动（见 5.1 接口预留）。

### 3. 出库（6 个）★ 技术主战场

| # | 功能 | 说明 | 数据 | 标记 |
|---|---|---|---|---|
| 3.1 | 订单管理 | 客户订单 + 明细；用真实 **32,634 个订单** | ✅ 真实 | 🔴 |
| 3.2 | **分配库存** | 为订单行分配具体库位 → 生成分配明细 | ✅ 可推导 | 🔴 |
| 3.3 | **波次生成** | 合并订单成波次（容量 **27 件**） | ✅ 真实 9,707 个 | 🔴 |
| 3.4 | **拣货任务** | 按库位聚合分配明细 → 拣货员视角的取货指令 | ✅ 真实 | 🔴 |
| 3.5 | **拣货确认** | 库存 allocated → picked（**总数不变**） | ✅ 真实 | 🔴 |
| 3.6 | 发货确认 | 出库，库存 qty 扣减 + picked 扣减 | ⚠️ 构造 | 🟡 |

**技术落点**：
- 3.2 分配库存 → **并发扣减（条件更新 WHERE qty_available >= N）**
- 3.4 拣货任务 → **路径优化的输入**（按库位聚合，见数据验证：聚合后节省 52% 行走次数）
- 3.5 拣货确认 → **并发扣减 + 幂等**

### 4. 库存（4 个）

| # | 功能 | 说明 | 标记 |
|---|---|---|---|
| 4.1 | 库存查询 | 按商品/尺码/库位查，显示**五个数量** | 🔴 |
| 4.2 | 库存流水 | 每次变动记录，含**来源单据类型 + ID**（可追溯） | 🔴 |
| 4.3 | 冻结/释放 | qty_onhold 增减（手工冻结，如质检不合格） | 🟡 |
| 4.4 | **超时释放** | 定时任务扫描超时未拣货的分配，自动释放 allocated | 🟡 |
| 4.5 | **盘点** | 盘点单（选商品/库位 + 填实盘数）→ 系统算差异 → 调整库存 | 🔴 |

**核心设计：五字段库存模型**
```
qty（现有） / qty_allocated（已分配） / qty_picked（已拣出） / qty_onhold（冻结） / qty_available（可用）
```

### 5. 算法模块（2 个）★ 项目卖点

| # | 功能 | 说明 | 基准 | 标记 |
|---|---|---|---|---|
| 5.1 | **货位分配优化** | 以最小化拣货行走距离为目标分配库位 | **数据集自带 4 种存储策略** | 🔴 |
| 5.2 | **拣货路径优化** | 波次内最短拣货顺序 | **S形 / 最大间隙 / 返回式** 三种行业标准 | 🔴 |

> **为什么是这两个**：都是纯组合优化问题，**基准现成**（数据集自带 / 行业标准），最容易讲出可量化的成果。

### 6. Agent 层（2 个）★ 调 LLM API

| # | 功能 | 说明 | 标记 |
|---|---|---|---|
| 6.1 | **自然语言查询** | 用户用中文提问 → LLM 理解意图 → **调用工具查库** → 生成中文回答 | 🔴 |
| 6.2 | **异常诊断解释** | 统计规则检测异常 → LLM 生成人话诊断建议 | 🟡 |

**技术形态**：**Function Calling / Tool Use**（LLM 不直接算数，而是决定调用哪个工具）
**模型**：通义千问 qwen-plus（复用 RAG 项目的 key）

### 7. 报表（2 个）

| # | 功能 | 说明 | 标记 |
|---|---|---|---|
| 7.0 | **首页看板** | 库存总量、今日入库/出库、库位利用率、预警数 + 出入库趋势图 | 🔴 |
| 7.1 | **库位地图** | 用真实 XYZ 坐标画仓库平面图，货位占用着色 + **拣货热度** + 拣货路径叠加 | 🔴 |

> 富勒 WMS 有"按层/排/列"的图形化库存，我们用**真实三维坐标**，效果更直观。

## 三、只预留接口（⚪ 这轮不实现）

| 功能 | 预留方式 | 时间够时 |
|---|---|---|
| **需求预测** | `DemandService.predict(skuId, days)` → **规则桩返回移动平均** | 接 ADI/CV² 分类 + Holt-Winters/Croston |
| **补货建议** | `ReplenishService.suggest()` → 规则桩返回固定阈值 | 接需求预测结果 + 成本优化 |

**规则桩的作用**：保证**不依赖 Python 也能完整跑通业务**（每阶段都有可交付产物）。

## 四、明确不做（❌）

| 不做 | 理由 |
|---|---|
| 采购管理 / 销售管理 / 财务管理 | ERP 职责 |
| 经营看板（成本/金额） | 要造数据，性价比低 |
| 库存调拨 | 单仓场景下与上架逻辑重合 |
| 质检追溯 / 批次效期 | 无数据 |
| 多仓库 / 月台管理 / 越库 | 边缘功能 |
| 复核台（称重/拍照） | 需要硬件 |
| PDA / RF 手持端 | 需要设备 |
| 打印（面单/条码） | 非研发重点 |
| 客户管理 / 拣货员管理（独立模块） | 作为字段展示即可 |
