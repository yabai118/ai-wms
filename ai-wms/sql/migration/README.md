# 迁移脚本

## ⚠️ 这是给【存量库】用的，全新安装不要跑

**全新安装请直接用 `../schema.sql`** —— 它已经是当前完整的 22 张表结构。

```
全新安装：    mysql < sql/schema.sql          ← 一步到位
存量库升级：  mysql < sql/migration/01_add_auth.sql
             mysql < sql/migration/02_add_rbac.sql
             mysql < sql/migration/03_rename_operator_to_staff.sql
```

**为什么新库不能跑**：这些脚本记录的是「**从旧结构改到新结构**」的过程。
比如 `01` 会建一张**老形态**的 `sys_user`（带 `username`/`display_name`），
而 `schema.sql` 建的已经是新形态了 —— 硬跑会冲突。

---

## 为什么保留它们

**迁移脚本是"结构变更的历史记录"**，有独立价值：

1. **存量库升级** —— 别人（或你自己的另一台机器）有一个旧结构的库，照着跑就能升上来
2. **面试可讲** —— 「每次改表结构都留一个编号迁移脚本，附带背景和取舍」，
   这是正经项目的做法。三个脚本的注释里都写了**为什么改**，比"改了啥"更有价值
3. **`03` 尤其值得看** —— 它记录了「账号模型为什么从三个字段塌缩成一个外键」
   的完整论证，包括"为什么强制关联到员工（含管理员）"

---

## 脚本清单

| 编号 | 做了什么 | 关键决策 |
|---|---|---|
| `01_add_auth.sql` | 新增 `sys_user`，补上系统缺失的登录能力 | 账号与人员**分两张表**（`operator` vs `sys_user`） |
| `02_add_rbac.sql` | 角色从 Java 常量改成表（`sys_role` / `sys_role_permission`） | **权限的定义留在代码**（对应接口），**分配放进数据库**（可配） |
| `03_rename_operator_to_staff.sql` | 账号模型重构：`operator` → `staff`，三个字段塌缩成 `staff_id` | **强制关联**（含管理员）—— 管理员权限最大，最该追责 |

---

## 维护约定

**改了表结构之后，两处都要动：**

1. `../schema.sql` —— 更新成最新结构（给新用户）
2. `migration/` 下加一个**新编号**脚本 —— 记录怎么从旧改到新（给存量库）

**只改一处就会出现"生成出来的东西装不上"的问题** —— 这个坑踩过一次：
`schema.sql` 停在了旧结构，而代码早就用上新表名了。
