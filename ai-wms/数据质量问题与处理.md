# 数据质量问题排查与处理方案

> 触发原因：建表后做全面数据体检，发现 7 个问题
> 排查时间：2026-09-17
> 结论：**1 个是严重格式问题（已找到规律并验证），其余为可控的数据缺口**

---

## 🔴 问题 1（严重）：`Size (US)` 字段存在两种格式混用

### 现象

```
尺码取值范围：1.0 ~ 305.0     ← 鞋码不可能到 305
其中 >20 的记录：41,549 条（占 34%）
涉及订单：15,592 个（占 48%）
```

取值分布：
```
75, 85, 95, 105, 115, 125        （间隔 10）
215, 220, 225, 230, ... 305      （间隔 5）
```

### 根因

**小数点在数据导出时丢失**——同一个字段混用了两种格式：
```
正常记录：  8.5
异常记录：  85      ← 小数点被吞掉
```

### 验证过程

**证据 1**：还原后尺码变成完美序列
```
还原前：1.0 ~ 305.0   (45 种取值)
还原后：1.0 ~ 30.5    (45 种取值，取值数不变)
        → 1, 1.5, 2, 2.5, ..., 15, 16, 21.5, 22, ..., 30.5
```

**证据 2**：单个商品的尺码变成连续序列
```
商品 0LNUOV
  还原前: [7, 8, 9, 10, 11, 12, 13] + [75, 85, 95, 105]
  还原后: [7, 7.5, 8, 8.5, 9, 9.5, 10, 10.5, 11, 12, 13]  ← 完美连续
```

**证据 3**：SKU 数量不变、无冲突
```
还原前 SKU 数: 2,515
还原后 SKU 数: 2,515     ← 完全一致（双射）
冲突检查（同款同码对应多个原始值）: 0 个
```

### ✅ 处理规则

```python
size_real = size_raw / 10 if size_raw > 20 else size_raw
```

**验证：取值数不变、SKU 数不变、无冲突 → 规则正确。**

## 🟡 问题 2：`quantity (units) = 0`（33 条）

订单行数量为 0，无业务意义。

| | |
|---|---|
| 数量 | 33 条 |
| 样例 | 订单 107393 的多行，数量均为 0 |
| **处理** | **导入时过滤**（`WHERE quantity > 0`） |

## 🟡 问题 3：`Size (US)` 空值（16 条）

订单行没有尺码，无法定位到 SKU。

| | |
|---|---|
| 数量 | 16 条 |
| 涉及商品 | `4E1WTK`、`UMKYTJ` 等 |
| **处理** | **导入时过滤**（`WHERE size IS NOT NULL`） |

## 🟡 问题 4：波次用到 6 个不存在的库位

```
E-25-20, G-25-10, I-25-20, J-25-20, K-25-20, K-26-20
→ 这 6 个库位号在 Storage_Location.csv 里没有
```

另外还有 16 种**非标准格式**的库位（功能区）：
```
RC-01 ~ RC-05     ← 收货区（Receiving）
EX-01, EX-04, EX-11  ← 发货区（Export）
C-014, C-021~C-026, C-061, C-102  ← 中转区
ZN-COR            ← 角落区
```

| **处理** | 方案 |
|---|---|
| 6 个缺失的标准库位 | **补进 location 表**（标记为"数据补充"） |
| 16 种功能区 | **也建为库位**，`location_type` 设为收货区(2)/发货区(3)/其他 |

## 🟢 问题 5：77 个波次号在订单表有、波次表没有

```
订单表有 9,784 个波次号
波次表有 9,707 个波次号
差集 77 个（涉及 296 行、172 个订单）
波次表有但订单无: 0 个
```

**含义**：有 77 个波次的订单**从未被拣货**（可能取消了、或数据缺失）。

| **处理** | 保留订单，**不生成拣货任务**（状态标记为"未拣货"） |

---

## 🟢 问题 6 / 7：两个库位坐标完全相同

```
K-23-30   position=(102,810,3)
K-23-40   position=(102,810,3)   ← 与上面完全相同
```

推测是 `z` 值录入错误（40 应该是 z=4，但和 30 记成了同一个）。

| **处理** | **保留原样**（只影响地图上两个点重叠，不影响业务） |

## 三、对表设计的影响

| 表 | 是否要改 | 说明 |
|---|---|---|
| `product_sku.size_us` | ❌ 不改 | 类型 `DECIMAL(4,1)` 够用（最大 30.5） |
| `location` | ⚠️ **要补数据** | 补 6 个缺失库位 + 16 个功能区 |
| `location_type` | ✅ 已有 | 功能区用 2(收货区)/3(发货区) 表示 |
| 其他表 | ❌ 不改 | |

**只需改数据，不用改表结构。**

## 四、这次体检的价值（面试可讲）

> "建完表后我做了一次全字段数据体检，发现**尺码字段存在 34% 的异常值**（最大到 305）。
> 我没有直接过滤掉，而是**分析出了规律**——小数点在导出时丢失（`8.5` 变成了 `85`），
> 于是用 `>20 则 ÷10` 的规则还原，并**用三个证据验证**：还原后尺码变成连续的鞋码序列、
> 取值数不变、SKU 数不变且无冲突。
> 最后还发现 6 个波次用到的库位在库位表里缺失，一并补上了。"

**这段能体现**：数据敏感度 + 不轻易丢数据的严谨 + 用多重证据验证假设。
