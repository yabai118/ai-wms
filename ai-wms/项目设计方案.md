## 一、项目定位

### 场景

**巴西一家鞋类制造企业的成品仓库**。它面向 588 个客户，日均处理 **183 个订单**，仓库有 **2,292 个货位**、**208 个鞋款**（每款 12 个尺码左右）。

**当前痛点**（来自数据集论文原文）：
> 拣货波次的生成"**without grouping or optimization**"——按订单到达顺序机械组合，**完全没有优化**。

**这就是项目的切入点**：用算法优化波次组合、货位分配与拣货路径。

### 一句话定位

**数据驱动的智能仓储系统**——基于某鞋类制造企业**真实 WMS 导出的 32,634 个订单、9,707 个拣货波次、286 天作业数据**，Java 底座承载仓内作业与并发一致性，Python 层用运筹优化算法优化**需求预测、货位分配、波次生成、拣货路径**四类核心决策。

### 为什么站得住

| 质疑 | 回答 |
|---|---|
| "模拟项目，没有真实数据" | ✅ **真实企业 WMS 用 SQL 导出的生产数据**，论文可查（Data in Brief, 2025） |
| "Agent 只是外挂" | ✅ 四类决策全部切入主流程，且**直接解决了原系统"无优化"的痛点** |
| "应届生只会增删改查" | ✅ Java 侧有并发/一致性，Python 侧有编排+降级 |
| "和市面模板什么区别" | ✅ 市面 WMS 模板多为进销存（无货位/波次），本项目聚焦**真实仓内作业优化** |

## 三、业务场景与流程

### 3.1 核心流程（来自真实数据）

```
① 客户下单        → 订单池（588 客户 × 32,634 订单）
② 生成拣货波次    → 波次（容量 ≤ 27 件）★ 当前无优化
③ 分配拣货员      → 24 个操作员
④ 按波次拣货      → 按货位取货（每波平均 6 种商品 / 10.7 个货位）
⑤ 出库发货
```

### 3.2 补货流程（本项目新增）

```
需求预测 → 补货建议 → 采购/调拨入库 → 上架（货位分配）
```

### 4.2 技术选型依据

| 选型 | 依据 |
|---|---|
| **模块化单体** | 行业共识：微服务适用于团队 >30 人；中小型 WMS 用模块化单体保持强一致性 |
| **不引入 Seata / K8s / SkyWalking** | 单体用本地事务；微服务化后的配套设施对单人项目是负担 |
| **RocketMQ（单 MQ）** | 异步削峰 + 跨语言解耦，一个够用 |
| **Nacos（可选）** | 行业推荐第一阶段用 Spring Cloud Alibaba + Nacos 做服务治理 |

### 4.3 明确砍掉的技术

| 砍掉 | 理由 |
|---|---|
| **Milvus / 向量库** | 无 RAG 场景 |
| **LangGraph + AutoGen** | 职责重叠；编排自研更能体现理解深度 |
| **MCP** | 解决 M×N 集成问题；本项目 1×1，REST 更简单（官方文档明确支持此判断） |
| **Seata** | 模块化单体用本地事务 |
| **K8s / SkyWalking** | 运维收益低于成本 |
| **LSTM / Prophet** | 商品-日覆盖率仅 35.2%，间歇性需求，深度模型样本不足 |
| **gRPC / 双 MQ** | 技术选型要匹配规模 |

## 五、Java 业务底座（第一阶段）

### 5.1 模块划分

| 模块 | 职责 |
|---|---|
| **wms-basic** | 商品主数据（款 + 尺码）、货位主数据（编号/坐标/容量18） |
| **wms-inbound** | 入库单+明细、收货、**上架（含货位推荐）** |
| **wms-outbound** | 客户订单、订单行、**波次生成**、拣货任务、发货 |
| **wms-inventory** | 库存（SKU×货位）、货位占用、**冻结/释放**、库存流水 |
| **wms-alert** | 补货预警、异常告警 |

> **不做**：采购、销售、财务（ERP 职责）、质检追溯、多仓调拨、复杂审批流

### 5.2 ⭐ 库存粒度：SKU = 商品 × 尺码

这是**鞋类仓储的关键特征**：同一款鞋的 41 码和 42 码是**独立的库存单位**。

```
product (款)           : Reference='8N10W9', ABC='A'
    └─ sku (款×码)      : '8N10W9-41', '8N10W9-42' ... （2,515 个）
         └─ inventory   : SKU × 货位 × 数量
```

> 面试话术："鞋类仓储和普通电商不同——**同一个款的每个尺码都是独立库存单位**。我按 2,515 个 SKU 管理，而不是 208 个商品。"

### 5.3 库存冻结机制

出库分两步，避免"货未拣走、库存被抢"：

```
① 波次生成  → 冻结库存（可用 -N，实物不变）
② 拣货完成  → 扣减实物库存 + 释放冻结
③ 超时未拣  → 定时任务自动释放
```

```
inventory: quantity(实物) | frozen_quantity(冻结) | available = quantity - frozen
```

### 5.4 并发扣减防超卖

- **乐观锁**（`version`）打底 + **Redis 分布式锁**兜底
- **幂等**：订单号唯一约束

### 5.5 为 Python 层预留的接口契约

```java
public interface AgentGateway {
    DemandResult    predictDemand(String skuCode, int horizonDays);   // 需求预测
    SlottingResult  recommendLocation(String skuCode, int quantity);  // 货位分配
    BatchingResult  generateWaves(List<Long> orderIds);               // 波次生成 ★
    RoutingResult   optimizePickPath(long waveId);                    // 拣货路径
    AnomalyResult   detectAnomaly(OperationLogQuery query);           // 异常诊断
}
```

**规则桩**（保证不依赖 Python 也能跑）：预测→移动平均；货位→ABC 就近；波次→按订单顺序；路径→按货位编码顺序；异常→返回空。

## 六、Python 层：四个运筹优化模块 + Agent

### 6.1 决策层 vs Agent 层

**真实行业实践**（DHL 用 Agent 处理邮件电话、PUMA 用中央编排器做数据查询）表明：仓储 AI Agent 主要做**交互、查询和编排**，而**预测/分配/路径一直是运筹优化算法在做**——因为数值决策要**可解释、可复现、可验证**。

| 层 | 职责 | 技术 |
|---|---|---|
| **决策层（OR）** | 预测 / 货位 / 波次 / 路径 | 统计模型 / 优化 / 启发式 |
| **Agent 层** | 异常**检测**（统计）+ **解释**（LLM） | 见 6.5 |

### 6.2 编排层：Workflow 而非 Agent

依据 Anthropic《Building Effective Agents》"**找最简单的方案，只在必要时增加复杂度**"。本系统任务路由是**确定性**的，属于 **Workflow 的 Routing 模式**。

**编排器四职责**：① 路由 ② 上下文管理 ③ **结果校验**（预测值不能为负、波次不能超 27 件、货位不能超容量）④ 降级决策

---

### 6.3 ① 需求预测

- **粒度**：SKU（商品 × 尺码）日需求
- **数据**：286 天销量序列，**商品-日覆盖率仅 35.2%** → 间歇性需求
- **方法**：按 **ADI/CV²** 分类
  - ADI < 1.32（平滑需求）→ **Holt-Winters**
  - ADI ≥ 1.32（间歇需求）→ **Croston (SBA)**——标准指数平滑会被零值拖死
- **输出**：点预测 + **预测区间**（残差 bootstrap）
- **为什么需要区间**：补货是成本问题，算期望缺货量必须有分布

**补货决策**（无成本数据，用行业标准报童模型）：
```
期望总成本 = c_short × E[(D−Q)⁺] + c_over × E[(Q−D)⁺]
其中 c_short = 售价 × 缺货惩罚系数，c_over = 售价 × 持有成本率
```

### 6.4 ② 货位分配 ⭐ 有现成基准

- **数据**：2,292 个货位（XYZ 坐标）+ 2,515 个 SKU
- **目标**：最小化 `Σ(拣货频率 × 货位到月台距离)`
- **约束**：货位容量 18 个商品位、分区
- **方法**：
  - 基线：**ABC 分类**（A 类放最靠近月台）
  - 进阶：ABC + **商品关联度**（同一订单常一起出现的款放邻近）+ 容量约束贪心/匈牙利算法
- **⭐ 验证**：与数据集自带的 **4 种策略**（Random / Class_Based / Dedicated / Hybrid）**直接对比总行走距离**

> **这是本项目最硬的验证**——基准是行业标准的、现成的。

### 6.5 ③ 波次生成 + ④ 拣货路径 ⭐ 最有价值的模块

**问题背景**（论文原文）：现有 WMS 生成波次时 "**without grouping or optimization**"——按订单到达顺序机械组合。

**这是个真实的组合优化问题**（Order Batching Problem）：

| 子问题 | 内容 |
|---|---|
| **波次生成** | 32,634 个订单 → 组合成波次，每波 ≤ **27 件**（拣货车容量），使总行走距离最小 |
| **拣货路径** | 波次内 1~25 个货位 → 找最短拣货顺序 |

**拣货路径用行业三大标准策略**：

| 策略 | 做法 |
|---|---|
| **S形 / 穿越式** | 进入含货巷道就走到底 |
| **最大间隙** | 只走到巷道内最大间隙处折返（小订单量下平均最短） |
| **返回式** | 从巷道口走到最远货位再退回 |

**波次生成方法**：
- 基线：按订单到达顺序（**复现现有 WMS 的做法**）
- 改进：**基于商品关联度/货位邻近度的贪心聚类**（把拣货区域重叠的订单合并）

**⭐ 验证**：对比"现有做法（顺序组合）"vs"我的算法"的波次总行走距离

> **面试话术**："我先复现了企业现有的波次生成方式——按订单到达顺序机械组合。然后我用基于货位邻近度的贪心聚类改进，**在同样的订单集合上，波次总行走距离降低了 X%**。"

### 6.6 异常检测（Agent 层）

| 环节 | 方法 | 性质 |
|---|---|---|
| **检测**（是不是异常） | 3σ 统计偏差 / 规则（波次超时、拣货量与订单不符）/ 时序模式 | 🟢 确定性算法 |
| **解释**（为什么、怎么办） | **LLM 生成自然语言诊断建议** | 🔵 真正的 Agent 能力 |

**为什么这样分**：LLM 的强项是**把异常数据翻译成运维人员能看懂的诊断建议**，而不是做数值判断。**用 LLM 判断异常不可靠，用 LLM 解释异常才是正解。**

**数据支撑**：数据集含 operator、波次、时间戳 → 可推导"某拣货员波次耗时异常""某时段拣货量异常"。

**输出**：异常类型 + 严重级别 + 自然语言诊断 → 回写 `wms-alert`

### 6.7 跨语言通信

| 通道 | 场景 |
|---|---|
| **REST（同步）** | 实时性高（推荐货位） |
| **RocketMQ（异步）** | 耗时长（批量需求预测、波次生成、异常扫描） |

## 七、降级设计（三级管线）

```
请求 → [尝试算法] ──成功──▶ 返回
           ├─ 超时(>5s)  ──▶ ② 规则桩
           ├─ 抛异常     ──▶ ② 规则桩
           └─ 结果不合法 ──▶ ② 规则桩
                              └─ 规则也失败 ──▶ ③ 人工工单
```

> **规则桩**：预测→移动平均；货位→ABC 就近；波次→顺序组合；路径→S形策略

| **分类有效性** | 不分类 vs 按 ADI/CV² 分流 | 误差下降 X% |

| **⭐ 波次生成** | 现有顺序组合 vs 我的聚类 | 波次总距离下降 **X%** |
| **拣货路径** | S形 vs 最大间隙 vs 返回式 | 找出最优策略，距离差 X% |
| **降级有效性** | 主动 kill 服务 | 业务不中断，成功率 100% |

**两个带 ⭐ 的指标是最硬的**——因为**基准来自真实数据**，不是我编的。
