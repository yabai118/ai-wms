## 零、这次重新设计改了什么

### 0.1 一句话

> **原设计：把几个点在技术上做深（并发扣减、路径优化）。**
> **新设计：在此之上，把「策略」抽成层、把「异常」当流程、把「KPI」接成环。**

### 0.2 三个核心判断

| # | 判断 | 现状问题 |
|---|---|---|
| **1** | **策略必须从代码里抽出来，独立成层** | 上架策略硬编码 `used_slots < 18`、分配策略硬编码在 SQL 的 `ORDER BY` 里、波次聚合硬编码在 service —— 改一处要动全流程 |
| **2** | **异常要从「抛异常回滚」升级成「一等业务流程」** | 现在所有异常 = `BusinessException` + 整体回滚。业务要的是**可挂起、可追溯、可处理** |
| **3** | **KPI 链条要接通** | 业务考核什么 → 系统采集什么 → 报表展示什么。现在采集端缺失，报表只能出「好看的图」而不是「能考核的指标」 |

### 0.3 不做什么

**不推倒重来。** 现有的三个强项（并发扣减、路径优化、真实数据）**保留并作为新设计的支点** ——
尤其路径优化模块，它已经是「策略层」该有的形态，**直接作为其他三个策略的模板**。

## 三、业务流程

### 3.1 入库流程（5 步）

| # | 环节 | 为什么存在 | 系统要做什么 | 现状 |
|---|---|---|---|---|
| 1 | 到货通知 ASN | 人到货没到 / 货到没人卸，都是浪费 | 提前预知、预估库位 | ⚠️ 表有，无预约 |
| 2 | 收货验收 | 供应商送来的数不一定对 | 扫码点数、**差异处理** | ⚠️ 有 `received_qty`，**无差异处理** |
| 3 | 质检 | 不能等卖出去才发现是坏的 | 按规则判定、结果留痕 | ❌ **无** |
| 4 | 上架 | 放错了后面拣货全废 | **策略推荐库位** | ⚠️ **策略硬编码** |
| 5 | 库存更新 | 账实必须同步 | 实时增加、库位状态更新 | ✅ |

### 3.2 出库流程（7 步）

| # | 环节 | 为什么存在 | 系统要做什么 | 现状 |
|---|---|---|---|---|
| 1 | 订单接收 | 不能把不该发的发出去 | 库存校验、可分配量计算、异常订单拦截 | ✅ |
| 2 | 波次生成 | 一万单逐单拣，光走路就废了 | 订单**分组**、合单/拆单、优先级 | ⚠️ **分组成员靠人工选** |
| 3 | 拣货分配 | 决定从哪个库位扣、派给谁 | 库存分配、任务负载均衡 | ✅ |
| 4 | 拣货 | 别让拣货员自己找路 | **路径优化**、批次控制、防错 | ✅ **强** |
| 5 | 复核 | 拿错货发出去 = 客诉 + 赔钱 | **强制校验，不通过不让往下走** | ❌ **无** |
| 6 | 打包 | 箱子选错，运费白花 | 推荐箱型、称重体积、面单 | ❌ 无 |
| 7 | 发货 | 责任清晰、客户能查 | 扫码交接、状态回传 | ✅ |

### 3.3 已有的强项（保留）

```
上架 → 分配库存（条件更新防超卖）→ 生成波次 → 拣货 → 发货（唯一真正减 qty 的地方）
         ↑ 五字段全程流转                    ↑ Python 路径优化作用于此
```

**库存五字段模型**（`inventory` 表）：

| 字段 | 含义 |
|---|---|
| `qty` | 实物总量 |
| `qty_allocated` | 已被订单占用（未拣走） |
| `qty_picked` | 已拣出（未发货） |
| `qty_onhold` | 冻结（质检/异常锁住） |
| `qty_available` | 可用 = 总量 − 占用 − 已拣 − 冻结 |

**并发防超卖**：把判断写进 `WHERE` ——

```sql
UPDATE inventory
SET qty_allocated = qty_allocated + #{qty},
    qty_available = qty_available - #{qty}
WHERE sku_id = #{skuId} AND location_id = #{locationId}
  AND qty_available >= #{qty}        -- ★ 判断写进 WHERE，数据库行锁保证原子
```

**已验证**：150 线程抢 10 件库存 → **超卖 0 次**；
同一脚本换"先查后扣"实现（负面对照）→ **超卖 19 件、可用量变 −19**。
证明测试方法本身能发现问题，而非"跑一遍没报错"。

## 四、★ 策略层设计（本次核心）

### 4.1 为什么策略必须独立成层

**PM 对策略的要求是「可配置、可迭代」。** 这句话对架构有硬约束。

**现状 —— 策略散落各处：**

| 策略 | 现在的实现位置 | 形态 |
|---|---|---|
| 上架 | `InboundServiceImpl.recommendLocations()` | 硬编码 `used_slots < 18` |
| 分配 | `InventoryMapper.findAvailableLocations()` | 硬编码在 SQL 的 `ORDER BY` |
| 波次 | `WaveServiceImpl.generateWave()` | 硬编码，且**分组成员靠人工选** |
| 路径 | `wms-agent/app/services/routing.py` | ✅ **4 策略可枚举、可对比、有基准** |

**问题**：想把上架从"最空的库位"改成"ABC 分类"，**必须改 `InboundServiceImpl` 的业务代码** ——
改一处、测全流程，风险极高。

### 4.2 ⭐ 路径优化模块 = 已有的正确样板

`routing.py` 已经具备策略层该有的四要素，**它就是另外三个策略的目标形态**：

| 要素 | routing.py 的做法 |
|---|---|
| **策略可枚举** | `baseline` / `return` / `s_shape` / `largest_gap` 四个实现 |
| **可批量对比** | `compare_all()` 一次跑完全部策略 |
| **有评价基准** | `optimal_route()`（Held-Karp 精确解）—— 回答"离最优还差多少" |
| **统一接口** | `PickTask` 进，`RouteResult` 出，加策略不动调用方 |

> **设计要点：其他三个策略照这个形态做。**
> 这不是新发明，是**把项目里已经做对的那一套复制到另外三个策略上**。

### 4.3 策略层接口设计

```python
# 统一协议：输入业务对象，输出决策结果
class PutawayStrategy(Protocol):
    def recommend(self, sku: Sku, qty: int, n: int) -> list[Location]: ...

class AllocationStrategy(Protocol):
    def pick_locations(self, sku_id: int, need: int) -> list[tuple[Location, int]]: ...

class WaveStrategy(Protocol):
    def group(self, orders: list[Order], capacity: int) -> list[WavePlan]: ...
```

**三条约束**（照 `routing.py` 的规矩）：

1. **策略是纯函数** —— 输入业务对象，输出决策结果，不碰数据库
2. **每个策略必须能被独立对比** —— 同输入跑多策略，产出可比较的指标
3. **必须有评价基准** —— 没有基准就没法说"这个策略好"

### 4.4 ① 上架策略（新增）

| 项 | 内容 |
|---|---|
| **目标** | 提升空间利用率（减少库位浪费）+ 缩短后续拣货路径 |
| **影响因素** | ABC 分类、商品属性（重量/体积）、库位容量、商品关联性 |
| **数据依据** | ⭐ **286 天拣货历史 → 每个 SKU 出库频次 → ABC 分级** |

**现状问题（已核实）**：

- `recommendLocations` 硬编码 `used_slots < 18`，**上架推荐时没有用 `location.capacity` 字段**
  （`capacity` 只在"上架后累加封顶"和"展示占用率"用了）
- 代码注释自己写着：「【后续可升级】根据 ABC 分类、商品关联度做智能推荐」
- 只按"已用位数升序"排序 —— **等于随意放，没有业务规则**

**规则设计**：

```python
class ABCPutaway:
    """A 类（高频出库）→ 靠近出货口；C 类 → 远端"""

    def recommend(self, sku, qty, n):
        abc  = self.abc_of(sku)                    # 由 286 天拣货频次算出
        zone = {"A": 近端区, "B": 中部区, "C": 远端区}[abc]
        cands = [l for l in self.locations_in(zone)
                 if l.free_slots() >= qty]         # ★ 用 capacity，不用硬编码 18
        return sorted(cands, key=lambda l: (
            l.used_slots / l.capacity,             # ① 优先占用率低的（均衡）
            self.dist_to_exit(l),                  # ② 其次离出货口近的
        ))[:n]
```

**预期收益方向**（待实测）：

- 库位利用率提升（当前有大量库位从未被使用）
- A 类商品平均拣货距离下降 → **直接强化已有的路径优化成果**

### 4.5 ② 分配策略（抽出 + 补 FIFO）

| 项 | 内容 |
|---|---|
| **目标** | 保证先进先出；减少库存碎片 |
| **现状** | `ORDER BY l.location_type DESC, i.qty_available DESC` |
| **缺** | **FIFO / 批次** —— 库存表无批次字段，扣哪个库位与入库时间无关 |

**现状解读（这两条其实已经是策略了，只是没被当策略）**：

- `location_type DESC` = **拣货区优先** → 不用先去存储区补货，减少二次搬运
- `qty_available DESC` = **先扣满的库位** → 减少库存碎片（一个 SKU 散在 8 个库位，拣货员要跑 8 趟）

**目标规则**：

```python
class AllocationStrategy:
    ORDER = (
        "location_type DESC",     # ① 拣货区优先
        "inbound_time ASC",       # ② 入库早的优先 ← ★ 新增，FIFO
        "qty_available DESC",     # ③ 可用量降序（减少碎片）
    )
```

> ⚠️ **前置依赖**：FIFO 需要 `inventory` 增加**入库时间/批次**字段（见第八章）。

### 4.6 ③ 波次策略（补分组规则）

| 项 | 内容 |
|---|---|
| **目标** | 减少拣货路径 |
| **现状** | **人工选单** → 校验载具容量（≤27）→ 按 `(SKU, 库位)` 聚合 |
| **缺** | **分组规则** —— 现在"哪些订单分到一组"是人选的，不是系统算的 |
| **数据依据** | ⭐ **库位 x/y 坐标 → 订单货位重心距离** |

**聚合这一步已经做对了** —— 同库位的多个订单合成一条任务，这正是减少走动的关键。
**缺的是聚合之前的"分组"。**

**可选分组维度**（按可实现性排序）：

| 维度 | 数据是否具备 |
|---|---|
| ⭐ **区域就近**（货位挨得近的订单分一组） | ✅ **坐标现成** |
| 商品品类聚合 | ✅ SKU → 商品款 |
| 订单相似度（SKU 重合度高） | ✅ 订单明细现成 |
| 发货时效 / 物流公司 | ❌ 数据里没有 |

**规则设计**：

```python
class ProximityGrouping:
    """按货位空间距离聚类：货位挨得近的订单分到一组"""

    def group(self, orders, capacity):
        for o in orders:
            o.centroid = centroid([loc.xy for line in o.lines])   # 订单货位重心
        clusters = kmeans([o.centroid for o in orders])           # 或按库区粗分
        for c in clusters:
            for chunk in pack_by_capacity(c.orders, capacity):    # 容量 27
                yield WavePlan(orders=chunk)
```

### 4.7 ④ 补货策略（本期不做）

**不做，且要能说出为什么不做的理由：**

- 当前模型**没有区分"拣货位"和"存储位"**（`location_type` 有字段，但没有两级库存结构）
- 补货策略的前提是"存储区 → 拣货区"的两级结构，**没有这个前提，补货无从谈起**
- 强行做会变成"把 A 库位的货挪到 B 库位"，**没有业务价值**

> **这是有意识的取舍，不是遗漏。** 面试时要主动说。

### 4.8 策略评价基准

**没有基准就没法说"这个策略好"。** 路径优化模块已经给出示范：

| 策略 | 评价基准 |
|---|---|
| 路径 | Held-Karp 精确最优（已有） |
| 波次分组 | **不分组（每单单独拣）的行走距离** |
| 上架 | **现状（`used_slots` 升序）的库位利用率与拣货距离** |
| 分配 | FIFO 违反率、库存碎片度 |

> ⚠️ **待办**：路径优化的实验数字需**重跑定稿**。
> 脚本已改为「按 `(x, 拣货通道)` 去重」版本、可覆盖 100/100 波次；
> 但**磁盘上的 `路径优化实验报告.md` 仍是重建算法之前的版本**（覆盖 39 波次、
> 基线 7,064 米），与当前算法不一致。**重跑前不要引用该报告的数字。**

## 五、异常设计

### 5.1 现状：只有「报错」，没有「异常」

**已核实**：

- 所有异常路径 = 抛 `BusinessException` → `@Transactional` 整体回滚
- `outbound_order.status = 4`（已取消）**从未被任何代码写入**
- `location.status = 2`（锁定）**从未被任何代码写入**
- `InventoryMapper.releaseQty`（释放分配）**SQL 已写好，零调用**

> **PM 视角**：正常流程谁都会走，**异常分支才决定系统能不能上线**。
> 现在系统里没有"异常"这个概念，只有"失败"。

### 5.2 异常清单与处理规则

| 异常场景 | 现在 | 应有处理 |
|---|---|---|
| 收货**超收**（实收 > 预期） | 无 | 差异登记，确认后入库 |
| 收货**短收**（实收 < 预期） | 无 | 差异登记，通知采购 |
| 质检不合格 | 无 | 让步接收 / 退货 / 报损（**可配置**）|
| 复核不通过 | 无 | 退回拣货，记录差错 |
| **订单取消** | `status=4` 从未写入 | **释放已分配库存**（调用 `releaseQty`）|
| **库存不足** | **整体回滚** | **挂起订单**（`status=5` 新增），等补货 |
| 上架找不到库位 | 抛异常 | 允许人工指定（已有此路） |

### 5.3 订单挂起机制（最值得改的一条）

**现状**：库存不够 → 整个订单回滚 → 之前分配的库存全部还原 → 订单回到"待分配"。

**业务上应该**：库存不够 → **挂起**，货到了再发。

**为什么现在是这样**：因为整体回滚是"最简单正确的做法"，但它把**业务状态**和**技术事务**混为一谈了。

**改法**：

```
allocate(orderId):
  逐明细分配
  ├─ 全部分配成功 → status = 1（已分配）
  └─ 有缺货        → 保留已分配部分
                   → status = 5（挂起）★ 新增状态
                   → 记录缺货 SKU 与数量
                   → 不抛异常，不回滚
```

> ⚠️ 副作用修复：现在的 `AllocateResultVO.shortageSkus` **永远是空列表**
> （因为缺货就抛异常回滚，构造 VO 的代码走不到）。改成挂起后这个字段才有意义。

### 5.4 状态机补齐

```
入库单：待收货 → 收货中 → 待质检 → 质检中 → 待上架 → 已完成
                                     ↓
                                  质检不合格 → 待处理（让步接收/退货/报损）

出库单：待分配 → 已分配 → 拣货中 → 已拣货 → 已发货
          ↓         ↓
       库存不足 → 挂起(5)    已取消(4) ★ 两个状态目前都从未被写入
```

**设计原则：状态只能沿定义好的路径流转，不能跳。** 异常要有地方"待"。

## 六、KPI → 采集 → 报表

### 6.1 铁律

> **业务考核什么 → 系统就得采集什么 → 采集了才能出报表。**
> 反过来说：**某个 KPI 采不到数，这个 KPI 就是空话。**

### 6.2 KPI 清单与采集点

| 维度 | KPI | 需要采集 | 现状 |
|---|---|---|---|
| 库存准 | **库存准确率** | 盘点差异 | ❌ 空表 |
| 库存准 | **不超卖** | 分配失败日志 | ✅ 有 |
| 发货快 | 发货及时率 | 订单创建 → 发货时间 | ✅ 时间戳有 |
| 出错少 | **发货差错率** | 复核拦截记录 | ❌ 无复核 |
| 人效高 | **拣货人效** | 任务开始/结束时间 + 件数 | ⚠️ 部分 |
| 空间省 | **库位利用率** | 占用 / 容量 | ⚠️ 字段有，推荐时没用 |

### 6.3 报表设计

**现状**：Dashboard 有 4 张图（订单趋势 / ABC 分布 / 库区分布 / 库存 TOP10）——
**都是"分布图"，没有一张是"KPI 图"**。

**目标**：补 4 个 KPI 指标卡 + 2 张趋势图：

- 指标卡：库存准确率 / 发货及时率 / 发货差错率 / 库位利用率
- 趋势图：拣货人效趋势 / 库位利用率趋势

## 七、技术架构

### 7.1 分层

```
┌─────────────────────────────────────────────┐
│  前端  Vue3 + Vite + Element Plus + ECharts │
├─────────────────────────────────────────────┤
│  Java 业务底座  Spring Boot 3.2 + MyBatis-Plus │
│    controller（纯转发）→ service（业务编排）    │
├─────────────────────────────────────────────┤
│  ★ 策略层  ★ 本次新增的架构位置               │
│    上架 / 分配 / 波次（Java 侧）              │
│    路径（Python 侧，已有）                    │
├─────────────────────────────────────────────┤
│  Python 决策层  FastAPI + 运筹优化 + Agent    │
├─────────────────────────────────────────────┤
│  MySQL 9.3（19 张表）+ Redis（旁路缓存）      │
└─────────────────────────────────────────────┘
```

### 7.2 技术选型依据

| 技术 | 为什么是它 |
|---|---|
| Spring Boot 3 | 事务管理成熟，条件更新/行锁直接用 |
| MyBatis-Plus | 全注解 SQL（**无一个 XML**），自定义 SQL 用文本块写，可读 |
| MySQL 9.3 | **行锁 + 条件更新**是防超卖的基石 |
| Redis | 旁路缓存库存查询，**删缓存放在事务提交后**（避免脏读回填）|
| FastAPI | 运筹优化算法用 Python 生态最自然 |
| Vue3 + Element Plus | 后台管理系统组件齐全 |

### 7.3 明确砍掉的技术

| 技术 | 为什么不用 |
|---|---|
| 分布式锁（Redis/ZK） | 单库单表，**条件更新的行锁已经够**，加锁是多余开销 |
| RocketMQ | 没有异步解耦场景，同步调用够用 |
| Nacos / Seata | 单体应用，无服务治理与分布式事务需求 |
| K8s | 单机部署，**这个体量上 K8s 是给自己找麻烦** |

## 十、路线图

### 10.1 分期

| 版本 | 主题 | 内容 | 为什么这个顺序 |
|---|---|---|---|
| **1.0** | **策略层落地** | 抽策略接口 + **上架策略（ABC）** + **波次分组规则** | 数据最全、最能出数字，**且直接强化已有成果** |
| **2.0** | **异常闭环** | 收货差异 + 订单挂起/取消 + 质检 + 复核 | 补"业务完整度"，面试问异常答得出来 |
| **3.0** | **KPI 闭环** | 盘点实现 + KPI 采集 + 指标报表 | 前两步做了才有数据可采 |

### 10.2 为什么 1.0 排最前

**投入产出比最高**：

- 有**库位坐标**（每条拣货任务都有）
- 有 **286 天拣货历史**（算 ABC 分级）
- 有 `capacity` 字段（**目前闲置**）
- 有**现成的策略样板**（`routing.py`）

> **做上架策略不需要新数据，只需要把已有的用起来。**

### 10.3 工作量估算

| 项 | 工作量 | 说明 |
|---|---|---|
| 策略层接口抽象 | 小 | 照 `routing.py` 的形态 |
| 上架策略（ABC） | 中 | 需先算 ABC 分级（一次性离线计算）|
| 波次分组（区域就近） | 中 | 聚类算法 + 容量装箱 |
| 策略对比接口 | 小 | 照 `compare_all` |
| 分配策略补 FIFO | 中 | **需先改表**（加入库时间）|
| 订单挂起机制 | 中 | 状态机 + `releaseQty` 接线 |
| 收货差异 | 小 | 加字段 + 分支逻辑 |
| 质检模块 | 大 | 新表 + 流程 |
| 复核模块 | 中 | 新表 + 流程 |
| KPI 采集与报表 | 中 | 依赖前序 |
