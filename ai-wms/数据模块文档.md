| 项目 | 内容 |

### 为什么选这个数据集

| 候选方案 | 结论 |
|---|---|
| 菜鸟需求预测赛题数据 | 只有需求侧，无库位/作业数据 |
| UFMG 订单拣货基准 | 学术构造，非真实企业数据 |
| DataCo 供应链（18 万订单） | 真实，但无库位 |

**经过 8 个角度检索（学术/竞赛/开源/政府/ERP/医药/图书馆/供应链）确认：不存在同时满足「真实 + 库位 + 入库 + 库存 + 出库」的公开数据集。** 鞋厂数据集是覆盖最广的真实数据。

## 三、数据质量排查与处理

> 背景：建表后做全字段数据体检，发现 7 个问题。

### 问题汇总

| # | 问题 | 数量 | 严重度 | 处理 |
|---|---|---|---|---|
| 1 | `Size (US)` 格式混用 | 41,549 条 | 🔴 严重 | **还原：>20 则 ÷10** |
| 2 | `quantity = 0` | 33 条 | 🟡 | 过滤 |
| 3 | `Size (US)` 空值 | 16 条 | 🟡 | 过滤 |
| 4 | 波次用到 6 个不存在的库位 | 6 个 | 🟡 | 补进库位表 |
| 5 | 77 个波次号无拣货记录 | 77 个 | 🟢 | 保留订单，无拣货任务 |
| 6 | 两个库位坐标完全相同 | 2 个 | 🟢 | 保留原样 |
| 7 | 非标准编码的功能库位 | 16 个 | 🟡 | 建为正式库位 |

---

### 🔴 问题 1：`Size (US)` 字段格式混用（最严重）

**现象**
```
尺码范围：1.0 ~ 305.0      ← 鞋码不可能到 305
其中 >20 的记录：41,549 条（占 34%）
涉及订单：15,592 个（占 48%）
```

**根因**：**小数点在数据导出时丢失**——字段混用了两种格式
```
正常记录：8.5
异常记录：85      ← 小数点被吞掉
```

**验证过程（三重证据）**

**证据 1：还原后尺码变成合理序列**
```
还原前：1.0 ~ 305.0（45 种取值）
还原后：1.0 ~ 30.5 （45 种取值，取值种数不变）
        → 1, 1.5, 2, 2.5, ..., 15, 16, 21.5, 22, ..., 30.5
```

**证据 2：单个商品的尺码变成连续序列**
```
商品 0LNUOV
  还原前：[7, 8, 9, 10, 11, 12, 13] + [75, 85, 95, 105]
  还原后：[7, 7.5, 8, 8.5, 9, 9.5, 10, 10.5, 11, 12, 13]   ← 完美连续
```

**证据 3：SKU 数量不变且无冲突**
```
还原前 SKU 数：2,515
还原后 SKU 数：2,515     ← 完全一致（双射）
冲突检查（同款同码对应多个原值）：0 个
```

**处理规则**
```python
size_real = size_raw / 10 if size_raw > 20 else size_raw
```

| `Size (US)` 为 NULL | 16 条 | 导入时 `WHERE size IS NOT NULL` |

### 🟡 问题 4 & 7：库位补充

**4a. 波次用到但库位表缺失的 6 个标准库位**
```
E-25-20, G-25-10, I-25-20, J-25-20, K-25-20, K-26-20
```

**坐标推断依据**（从 2,292 个库位实测出的编码规律）：
```
seg -> (x, z)：  11→(368,1)  12→(352,1)  13→(336,1)
                 21→(368,2)  22→(352,2)  23→(336,2)
                 30→(352,3)  40→(352,4)
(区, 排) -> y：唯一确定（300 个组合，0 个冲突）
```
缺失的 seg `10`/`20` 数据里不存在，按 `pos=0` 规律推为 `(352, 1)` 和 `(352, 2)`。

**4b. 16 个非标准编码的功能库位**
```
RC-01 ~ RC-05        收货区（Receiving）
EX-01, EX-04, EX-11  发货区（Export）
C-014, C-021~C-026, C-061, C-102   中转区
ZN-COR               角落区
```

**处理**：全部建为正式库位，`location_type = 1`（拣货区），坐标分配在拣货区内。

**补充量**：2,292 + 6 + 16 = **2,314 个库位**

## 四、数据探索发现

### 4.1 冷热分区（重要）

**48% 的库位从未被拣货使用**：

```
区    库位数   使用率
A~G   580      0%      ← 完全未使用 → 判定为【存储区】
H      88      35%
I~R  1,404    54~76%   ← 实际拣货区
```

**结论**：真实仓库存在**储备区 vs 拣货区**的分工。据此在 `location` 表增加 `location_type` 字段：
```
584 个存储区（A~G）  /  1,730 个拣货区（H~R + 功能区）
```

### 4.2 ABC 分类与拣货频率强相关

```
等级   商品数   占比     拣货次数占比   平均拣货次数
A      44      21.2%    40.7%         1,990 次
B      70      33.7%    29.3%           902 次
C      94      45.2%    30.0%           686 次
─────────────────────────────────────────────
A 类平均拣货次数是 C 类的 2.9 倍
```

**21% 的商品贡献 41% 的作业量**——经典二八法则，验证了 ABC 分类的有效性，也是**货位分配算法的依据**。

### 4.3 `RC-01` 是特殊商品专属区

```
RC-01 被拣 22,979 次（全场最高频，占总拣货 10.7%）
其中 PY5UPB 一个商品占 12,063 次（52%）

对照：PY5UPB 总拣货 13,380 次，90% 来自 RC-01
对照：普通商品 8N10W9 拣货 18,069 次，分布在 62 个库位（最热占 11%）
```

**结论**：`PY5UPB` 是**大码鞋**（尺码 21.5~30.5），有专属存储区。真实仓库中特殊商品会单独划区。

### 4.4 波次容量超标

```
波次件数：min=1  max=30  avg=22.2
超过论文所述"载具容量 27"的波次：74 个
```

**处理**：保留原样（真实作业中存在加车/分批），设计算法约束时以实际数据为准。

### 4.5 其他发现

| 发现 | 说明 |
|---|---|
| `sector` 字段全是 `PF` | 无信息量（所有商品同属一个分区） |
| 同一库位在一个波次内被重复访问 | 36.7% 有重复，**聚合后节省 52% 行走次数** |
| `Support_Points` 揭示通道位置 | LC 系列 x=66，CC 系列 x=403 |

### 5.2 四个关键设计

**① `product_sku` 独立成表**
```
product:      8N10W9（款）
product_sku:  8N10W9-41、8N10W9-42...（2,515 个）
              ↑ 库存挂在这层（鞋类特征：同款不同码是独立库存单位）
```

**② `inventory` 五字段模型**
```sql
qty            现有总量      -- 拣货时不变
qty_allocated  已分配        -- 防超卖
qty_picked     已拣出
qty_onhold     冻结          -- 与 allocated 分离（正常占用 vs 异常冻结）
qty_available  可用          -- = qty - allocated - onhold
version        乐观锁版本号
```

**③ `outbound_allocation` vs `picking_task`**
| 表 | 视角 | 行数 | 回答 |
|---|---|---|---|
| `outbound_allocation` | 订单视角 | 待生成 | 这张订单的货从哪取 |
| `picking_task` | **库位视角** | 112,977 | 拣货员走哪些库位、各取多少 |

（数据验证：同库位在波次内重复访问 36.7%，聚合后省 52% 行走）

**④ `inventory_transaction` 记 `reference_type + reference_id`**
```
库存变了 → 查流水 → 知道是哪张单导致的
库存数字 → 用流水重算 → 对账验证一致性
```

### 5.3 设计原则

| 原则 | 说明 |
|---|---|
| **逻辑外键** | 只建索引，不建物理外键约束（避免性能损耗与迁移麻烦） |
| 字符集 | utf8mb4 |
| 审计字段 | 关键表带 `created_at` / `updated_at` |

## 十、面试问答预案

### Q1：数据哪来的？

> "巴西一家鞋类制造企业**真实 WMS 系统导出的订单拣货数据**，论文发表在 *Data in Brief*（CC BY 4.0 开源许可）。
> 包含 208 个鞋款、2,292 个带三维坐标的库位、32,634 个订单、9,707 个拣货波次，跨 286 天。"

### Q2：数据质量怎么样？怎么处理的？

> "建完表后我做了**全字段数据体检**，发现**尺码字段有 34% 的异常值**（最大到 305）。
> 我**没有直接过滤**，而是分析出规律——小数点在导出时丢失（`8.5` 变成 `85`），用 `>20 则 ÷10` 还原，
> 并**用三个证据验证**：还原后尺码变成连续序列、取值种数不变、SKU 数不变且无冲突。
> 还发现 6 个波次用到的库位在库位表里缺失，按编码规律补上了。"

### Q3：为什么不找一份"完整"的数据集？

> "我检索了 8 个角度（学术/竞赛/开源/ERP/医药/图书馆等），**不存在同时满足「真实 + 库位 + 入库 + 库存 + 出库」的公开数据集**。
> 要么是真实但只有片段，要么是完整但明确标注 synthetic。
> **我选择真实数据 + 构造补齐**，并且明确标注哪些是真实、哪些是构造的。"

### Q4：你的数据里有什么业务洞察？

> "三个：
> ① **48% 的库位从未被使用**（A~G 区完全闲置）——说明存在储备区/拣货区分工，我据此在模型里加了库位类型；
> ② **21% 的商品贡献 41% 的作业量**——二八法则，这是货位分配算法的依据；
> ③ **同一库位在一个波次内平均被访问多次**（36.7% 有重复），聚合后能**节省 52% 的行走次数**——这是我设计"拣货任务"表的依据。"
